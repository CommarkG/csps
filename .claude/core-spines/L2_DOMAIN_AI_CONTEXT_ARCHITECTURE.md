# L2_DOMAIN_AI_CONTEXT_ARCHITECTURE

Operational decomposition of AI spine — the domain governing **context as the platform's
primary navigation mechanism**.

## What this domain governs

Context is not optional metadata — it is the primary mechanism by which the AI distinguishes correct behavior from plausible behavior. P-META-020 (L1) established that context is the compass. This L2 domain defines HOW context is created, maintained, transferred, and verified at every platform boundary.

The domain answers 4 operational questions that P-META-020 leaves to implementation:
1. **What is the context SSoT per session?** → session-context-record.md (generated at session open)
2. **How is context declared at proposal time?** → OD-008 disposition: override (context before proposing)
3. **How are questions the primary context-transfer mechanism?** → question_register field + 8 question types
4. **How is context transferred at scope transitions?** → explicit context_transfer declaration at S0→S1→S2

## Operational Governance Surfaces

**session-context-record.md** — Per-session SSoT (generated by session-open.sh). Contains:
- Active governing contexts (scope_level, principles, PE top-3)
- Open requests from governor-request-ledger.yaml sorted by PE
- Context gaps detected this session
- Questions asked → context captured

**OD-008 (output-distribution.md)** — Context declaration at proposal time:
- Before any substantive AI proposal: "Governing context: [principle] at [scope]. Operating assumption: [X]. Uncertainty: [what I don't know]."
- disposition: override (training default is to propose without declaring context)
- Caught by: reasoning-scope-level-awareness (LIVE) + virtual-opus-audit COMP-4

**question_register field** (plans + artifacts) — 8 question types as context carriers:
- C-type: goal context | Z-type: completion context | G-type: gap context
- R-type: risk context | B-type: background context | A-type: assumption context
- P-type: precedent context | X-type: cross-domain context
- Enforced: validate-question-coverage.mjs (LIVE)

**Context transfer at scope transitions** — When work moves between scope levels:
- S0→S1: what constitutional constraints carry down
- S1→S2: what platform patterns the app inherits
- Each transition: `context_transfer: from_scope: S0 → to_scope: S1 | inherited: [...] | new: [...]`

**Cross-entity boundary transfer (ZCA — P-UX-002)** — When context crosses between INDEPENDENT entities (separate AI tabs, separate sessions, external APIs, EKEP exchanges): the receiver starts from zero. WHO/WHAT/HOW/NOW is mandatory before any task content. Scope transitions above are internal (same entity, different layer); ZCA governs external crossings where the receiver has no prior state. See: [boundary-assumptions.md](../plan/_handoff/VAULT/inner-ai-defaults/boundary-assumptions.md) + [ai-transfer-template.md](../plan/_handoff/VAULT/templates/ai-transfer-template.md).
