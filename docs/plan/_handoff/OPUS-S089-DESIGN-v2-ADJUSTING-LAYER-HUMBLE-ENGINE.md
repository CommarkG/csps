# OPUS S089 — Design v2: The Adjusting Layer + the Humble Engine

> Governor S089 directive: define triggers → simulate pipelines → spec the routing orchestrator →
> design the inward/outward adjusting layer → external-AI feedback BEFORE build. Hardwire
> "all is core universal wisdom + alignment-to-existing + optimization" into HOW this is built.

## 0. NORTH STAR — the platform builds itself with its own tools (governing principle)
CSPS's core goal: a platform that uses **its own tools to build itself**, creating every solution from the
platform's **core DNA + tools** — not beside them. Every S089 stream is built BY the platform:

> A new solution enters via the **Threshold** (universal entry) → the **Humble Engine** decides
> create-vs-enhance using **CIE** (what exists) + **PE** (rank) → the **Journey** runs the build →
> **Tagging-core** binds its vocabulary → **Validators + IZFC + two-party seal** gate it → the
> **Adjusting Layer** governs what it absorbs (inward) and emits (outward).

**Recursive dogfood:** the Synergy/comparison engine, once built, becomes *another platform tool* used to
compare and select future solutions (internal + external). The Humble Engine is both a thing-we-build **and**
the tool we build it WITH. If a stream can't be built by composing existing platform tools, that's a signal —
either a missing universal tool (promote it) or scope creep (cut it).

### Universal core (reused every time) vs Specific (one domain/element)
| UNIVERSAL CORE TOOLS — platform DNA, reused multiply | SPECIFIC — one domain/element |
|---|---|
| Threshold (entry) · Adjusting Layer (in/out membrane) · Humble Engine + CIE + PE triangle · Tagging-core / schema-registry / canonical-concepts (vocabulary) · Journey core (work-running) · Validators / verify / IZFC / two-party seal (QC) · UX/UI DNA (5 laws + UI principles) | App-comparison schema (schema.org merge) · synergy dashboard UI surface · bundling slot-dialogue · domain enums + domain-specific validators · MindMePA PE/orchestrator schema (stays in MindMePA's track) |

**Rule:** build SPECIFIC only by COMPOSING UNIVERSAL. The plan documents universal tools in full (they pay
off many times) and specific elements only to the depth their single use requires.

### Plan shape: minimal-now, full-detail-later
- **NEAR (minimal, concrete):** S2 UX/UI principles page — smallest surface, pure composition of UX/UI DNA;
  proves the self-build loop end-to-end on a low-risk artifact.
- **LATER (full detail):** S3 synergy + S4 Humble Engine — the reusable platform tools; full design once the
  council feedback + the **significance-threshold function** (§9 load-bearing gap) are resolved.

## 1. The unifying insight
The **Humble Engine** (inward-facing) and the **Adjusting Layer** (outward-facing) are **one membrane**:
- **Inward** — nothing new enters the core without being compared to what exists, consolidated, and
  significance-throttled. The core is never overwhelmed by external insight.
- **Outward** — everything the platform emits is expressed as *aligned core universal wisdom*, not as
  foreign bolt-ons. External knowledge is absorbed, aligned, then spoken in the platform's own voice.

This is **consolidation-over-creation, made automatic and bidirectional.**

## 2. The Adjusting Layer (consolidates existing mechanisms — not new machinery)
It NAMES and unifies what CSPS already has, into one membrane:
| Direction | Function | Consolidates (existing) |
|---|---|---|
| **Inward** | quarantine → align → compare-to-existing → consolidate → significance-throttle | DNA-Guardian (quarantine), threshold intake (classify/route), humble-consolidation, organic-significance-accumulation, CS9 claim-until-reproduced |
| **Outward** | express as aligned core wisdom; default+variety; never insist | frictionless-communication DNA, ideas-not-insistence, platform-attitude (default+variety), CSPS-alignment-over-inner-defaults |

**Hardwire principle (HW-S089):** every ingress of external content/insight (apps, research, council, MCP,
user docs) passes the inward membrane; every egress (outputs, recommendations, pages) passes the outward
membrane. Enforced by: threshold gate (ingress) + a new `validate-adjusting-layer` (egress: outputs that
introduce un-aligned external vocabulary BLOCK until registry-bound).

## 3. The Humble Engine — platform-wide create-vs-enhance service (CIE + PE synergy)
**Today:** "consolidation/enhancement over new creation" is a manual discipline (B_NO_INVENTION_WITHOUT_PRECEDENT).
**v2:** make it an **engine every creation/enhancement pipeline calls**, before anything new is authored.

### The synergy triangle (the "new synergy" Q3 asked for)
```
        CIE  ──what already exists / related concepts──▶  HUMBLE ENGINE
   (concept intelligence)                                (compare + present options, humbly)
        ▲                                                      │
        │ records decision + new concept                       ▼ ranked options
        └──────────────  PE  ◀── score: create vs enhance vs consolidate (u×i÷e) ──┘
                    (priority engine)
```
- **CIE** supplies *what exists* (the precedent set + related concepts) — the engine never compares blind.
- **Humble Engine** runs the comparison and emits **options** (create-new / enhance-existing / consolidate /
  reuse) each with rationale + provenance — never a single insisted answer.
- **PE** scores the options (urgency×impact÷effort); the highest-PE option is *recommended*, not forced.
- Decision feeds back to CIE (new concept or enhancement recorded). **This triangle is the create-vs-enhance
  governance loop**, callable by ALL pipelines: threshold intake, journey creation, validator/page authoring,
  and the external-apps comparison.

### Two applications of ONE engine
1. **Internal** — "should we create this new, or enhance/consolidate existing?" (governance at every creation point).
2. **External** — "compare these external apps/solutions against the user's needs" (the synergy dashboard).
Same machinery: compare candidates → present humble options → rank → provenance. Build once, serve both.

## 4. Triggers → pipeline simulation → routing orchestrator (end-to-end)
### 4.1 Trigger taxonomy (what activates a pipeline)
| Trigger | Source | Activates |
|---|---|---|
| external-content-ingest | upload-once / MCP / research | inward membrane → tag → EvidenceDoc |
| creation-or-enhancement-intent | any authoring (page, validator, journey, concept) | Humble Engine triangle |
| comparison-request | user asks "compare X" | synergy compare → bundling orchestrator |
| user-need-elicitation | user starts a bundle | slot-filling dialogue |
| egress-emit | any output to user/app | outward membrane → alignment check |

### 4.2 Pipeline simulation (the whole process, start→end) — to validate before build
`trigger → classify (threshold) → inward membrane (quarantine/align/compare via CIE) → Humble Engine
(options) → PE (rank) → routing orchestrator (dispatch to the right pipeline/persona) → produce →
outward membrane (align expression) → IZFC seal → deliver`. **We will literally simulate this on 2-3
sample inputs (a sample external app, a sample new-page request) and record the trace before building.**

### 4.3 Routing orchestrator — how it decides
A deterministic dispatcher (no clock/cadence in the decision): input's `(spine, scope, intent, trust_level)`
→ lookup routing table → target pipeline + model-tier + persona. Extends the existing threshold router; the
orchestrator is its execution arm. Spec'd as a pure function (B_DETERMINISTIC_GATE).

## 5. UI principles (explicit — alongside the 5 UX-DNA laws)
The 5 UX laws (B_UX_UI_DISCIPLINE) govern *experience*; these govern *interface*:
1. **Visual hierarchy** — primary action above the fold; one clear next action per surface.
2. **Cause-effect colocation** — control and its effect/result rendered together (existing DNA).
3. **Progressive disclosure** — depth on demand; never wall-of-content.
4. **Design-token consistency** — all surfaces use the sacred `styles.css` tokens; no ad-hoc styling.
5. **State completeness** — loading / error / empty / success states for every data surface (M-47).
6. **Accessibility & responsive** — keyboard, contrast, semantic HTML; mobile-first.
→ Surface as a UI section in the UX-Principles page; gate with `validate-ux-audit` extension.

## 6. schema.org vs CSPS — PCR (Q4)
- **schema.org `SoftwareApplication`**: battle-tested, interoperable, machine-readable, SEO/structured-data,
  zero-invention. *Lacks*: provenance/trust, requirement (UserNeed) modeling, governance binding.
- **CSPS-native**: rich governance (EvidenceDoc provenance, trust_level, tagging-core binding, UserNeed,
  demonstrated-truth). *Lacks*: external interop, ecosystem adoption.
- **RECOMMENDATION — MERGE (hybrid):** adopt schema.org `SoftwareApplication` (+ `Offer`/`AggregateOffer`,
  `featureList`) as the **interop core of the App entity**, and **extend** with CSPS-native entities that
  schema.org has no concept of — `EvidenceDoc` (provenance), `UserNeed`, `ComparisonResult`, `Bundle`,
  `trust_level`. All extensions register in tagging-core. Net: interop where the world has a standard,
  CSPS depth where we add real value. **This exact question goes to the external AIs for challenge.**

## 9. Opus baseline positions (pre-council) — evaluate external feedback AGAINST these
*Recorded so incoming council feedback is judged as a peer claim on merit, not adopted blindly
(council-peer-contract + demonstrated-truth). The 3 MindMePA PE/Orchestrator feedbacks already
converge on the layered-PE-at-junctions pattern, pre-validating Q2/Q4.*

- **Q1 (Adjusting Layer):** RIGHT abstraction, but **ship minimal** — it is not new machinery, it NAMES
  existing gates (threshold + DNA-Guardian + humble-consolidation + frictionless-comm). Minimal = threshold
  front door (inward) + egress alignment check (outward). Over-build risk = a heavy new subsystem; reject that.
  Prior art to expect: API gateways, content-moderation pipelines, RAG ingestion with trust-tiering, immune systems.
- **Q2 (Humble Engine):** Sound; independently validated by the 3 MindMePA feedbacks (PE stays universal,
  consumed at explicit junctions). Failure modes: (a) gates every creation → friction (fix: SWIFT path; gate
  only significant creations); (b) CIE blind spot → false "nothing exists" → wrongful create (fix: precedent
  confidence + human fallback); (c) over-triggering (fix: explicit minimal junctions + debounce); (d) PE score
  gaming (fix: deterministic weights + audit).
- **Q3 (schema.org vs CSPS):** **MERGE** — schema.org SoftwareApplication core (interop) + CSPS extensions
  (EvidenceDoc/UserNeed/trust_level/Bundle), all bound to tagging-core. Unchanged from §6.
- **Q4 (deterministic dispatcher):** Robust IFF truly pure (no clock/mtime — B_DETERMINISTIC_GATE) + explicit
  versioned routing table. Breakers: intent ambiguity (fix: classifier confidence + fallback route), trust_level
  miscalibration, table drift. MindMePA feedbacks reinforce: deterministic > LLM scoring; re-evaluate only at junctions.
- **Q5 (bundling orchestrator):** hard-constraints = knockout filters; nice-to-have = MCDA weights (SAW/TOPSIS);
  slot-filling dialogue w/ completeness gate (≤2 Qs w/ reasons); ranked bundles + per-item explanation + coverage
  map + provenance; swing-weighting over raw sliders; show inferred weights back (editable-understanding).
- **Q6 (missing / over-building) — my honest self-critique:**
  - **Missing (load-bearing): the SIGNIFICANCE-THRESHOLD function is undefined** — what counts as "significant
    enough to gate creation" vs SWIFT-through. Without it the Humble Engine gates everything (friction) or nothing
    (no value). This is the highest-priority gap to close before build.
  - **Missing:** the `trust_level` taxonomy for the dispatcher isn't enumerated yet.
  - **Missing:** how the Humble Engine avoids becoming a per-creation bottleneck (perf + UX latency).
  - **Over-building watch:** the Adjusting Layer must stay a thin membrane over existing gates, not ceremony.
