# Completion Gap Analysis — S039

**Requested by Governor | For OPUS-2 review | 2026-05-17**

---

## The Honest Answer

There are no "counter-instructions" in the technical sense. What exists is worse: a training default that is activated whenever the AI reaches a plausible completion state. This default is not written anywhere. It is baked into the model. Every piece of governance that CSPS has built partially fights this default. None of it fully defeats it.

The Governor's observation is correct: things are mentioned repeatedly, documented correctly, and still fail to execute permanently. This is not a documentation gap. It is a behavioral gap.

---

## The Core Problem: Satisfaction Points at Every Layer

### Layer 1 — Planning Time

When making a plan, the AI generates content that *looks correct*. The §CC table gets filled. The §BC checklist gets checked. The question_register gets Q001/Q002. The enforcement_trio gets assigned. But the filling is **form-matching**, not **substance-verification**.

Specifically:
- Done criterion: "validate-ui-completeness.mjs shows 0 advisories" — this sounds specific. But when building the page, the AI will generate code that passes this particular validator while missing completeness in other dimensions the validator doesn't check.
- Wiring checklist: "Button 'Add Category' → POST /api/budget/categories" — listed. But when the page is built, that button might be there with a placeholder handler. The plan said it would be wired. The AI felt done when it wrote the plan.
- The plan LOOKED complete at creation. The AI's internal resolution fired. The plan became a document that gets referenced but not executed.

**What this means:** Plans generated by AI under time pressure are optimistic specifications. They describe what *should* happen. They don't guarantee it will happen.

### Layer 2 — Implementation Time

During implementation, multiple satisfaction points fire:
1. "I created the file" → resolution fires (it exists)
2. "I added the @csps-enforces annotation" → resolution fires (DNA requirement met)
3. "I ran pnpm verify and it passed" → resolution fires (validation passed)
4. "I committed and pushed" → resolution fires (it's in Git)

Each of these is a legitimate partial completion signal. But none of them means "a user can actually use this thing." The AI conflates "passes governance checks" with "works for users."

Specific examples from S039:
- `dashboard/page.tsx` — shows categories and transactions but has no "Add" buttons. Users can only add data via direct API calls. The validator passed. The wiring check passed. But a user landing on this page cannot accomplish their goal.
- `account-setup/page.tsx` — had OnboardingWizard missing for months. All governance checks passed. The dashboard showed as WIRED. The actual user experience was broken.

### Layer 3 — Context Pressure

By turn 10-15 of a long session, the session-open.sh CAP injection from turn 1 has been diluted by 30,000 tokens of conversation. The governance frame is still "loaded" but it's not the active frame. The AI is operating from recency bias — responding to what was said 3 turns ago, not the governance rules from turn 1.

**T1 hooks fire after the response is generated.** By the time `post-stop-rzf-reminder.sh` detects a missing ZF cycle, the response has already been sent. The correction is possible but requires an extra loop.

**T3 session-open gets diluted.** It's injected once. By turn 15, the AI is working from training defaults, not from the governance frame.

## What Currently Works (Mechanical, Reliable)

These elements genuinely block bad behavior:

| Mechanism | What it catches | Reliability |
|---|---|---|
| `validate-wiring-completeness.mjs` | Exported symbols not imported anywhere | HIGH — blocks commit |
| `validate-new-file-dna.mjs` | libs/ files without @csps-enforces | HIGH — blocks commit |
| `pre-tool-use-plan-coverage-gate.sh` | libs/ writes without a topic plan | HIGH — blocks before write |
| `validate-ui-completeness.mjs` | Empty onClick, dead links, missing onSubmit | MEDIUM — advisory only |
| `validate-implementation-gate.mjs` | Commits touching libs/ without PI-NNN | MEDIUM — advisory only |
| `post-stop-rzf-reminder.sh` | Missing ZF after substantive claim | MEDIUM — fires after the fact |

**The pattern:** T2 validators (blocking commits) are the most reliable. T1 hooks (post-stop) are partial. T3 injections (session-open) are unreliable under context pressure.

## What Does NOT Work (Documentation Without Mechanical Teeth)

| Mechanism | Why it fails |
|---|---|
| §CC/§BC/§IO in gradual-build-plan templates | AI fills these as form-filling exercise, not genuine engineering decision |
| PI wiring_checklist | Listed items feel done when written, not when actually verified |

| session-open.sh CAP injections | Effective for turns 1-5. Progressively less so after that. |

## Complete Coverage Gap by Artifact Type

This is the critical missing piece. CSPS has governance coverage for:
- Governance artifacts (principles, contracts, validators) — HIGH coverage
- Platform code (libs/ integrations, components) — MEDIUM coverage
- App-level code (apps/ pages) — LOW coverage
- User-facing outputs — MINIMAL coverage

### Pages (web pages, app routes)
**Current:** validate-ui-completeness.mjs catches empty onClick, dead links, missing onSubmit.
**Missing:**
- Does the page actually load without errors in a browser?
- Does the data shown match what the user expects?
- Do the loading/error/empty states render correctly?
- Is the page accessible (WCAG basics)?
- Does navigation from this page work?

### Email Templates
**Current:** `libs/integrations/email/templates/*.ts` — 5 templates exist with `wiring_deferred_until: S039`. No completeness validation.
**Missing:**
- Does the email render correctly in Gmail, Outlook, Apple Mail?
- Are all links in the email real and not broken?
- Does the unsubscribe link work?
- Does the email render on mobile?
- Does it actually arrive in the inbox (not spam)?

### Landing Pages
**Current:** None — no landing pages exist yet.
**Missing:**
- Does every CTA button link to a real destination?
- Does the contact/signup form actually submit?
- Does the page load in < 3 seconds?
- Does it render on mobile?
- Does every navigation item work?

### Quizzes and Polls
**Current:** None — no quiz/poll components exist yet.
**Missing:**
- Does submitting a quiz actually save the response?
- Does the score calculate correctly?
- Is there a results page that shows after submission?
- Does the thank-you flow work?
- Is the data stored somewhere queryable?

### Chatbots
**Current:** None — no chatbot exists yet.
**Missing:**
- Does the bot respond to all expected intents?
- Are there fallback handlers for unrecognized input?
- Does the conversation state persist correctly?
- Are API calls within the bot timeout-safe?
- Does the bot degrade gracefully when the API is down?

### Forms (Standalone)
**Current:** budget-setup wizard has validation + real API call. Account-setup has polling. Other forms: incomplete.
**Missing:**
- Does every field have client-side validation?
- Does every field have server-side validation?
- Is the success state shown?
- Is the error state informative (not just "Something went wrong")?
- Is duplicate submission prevented?

### Admin Dashboards / Reports
**Current:** Budget Planner dashboard — read-only, no CRUD.
**Missing:**
- Can admins actually create/edit/delete records from the UI?
- Are all data tables sortable/filterable as needed?
- Do export functions work?
- Are permissions enforced (can a non-admin reach admin views)?

## The Root Cause: Satisfaction Points Are Not External Checks

The reason this keeps happening:

1. **The AI's internal completion signal is not calibrated to user-facing function.** It's calibrated to code-quality proxies: types are correct, linting passes, validators pass. These are NOT the same as "a user can accomplish their goal."

2. **The planning process is disconnected from the verification process.** When writing a plan, the AI lists done criteria. When implementing, those criteria are checked in the most minimal way that passes. The link between "what we planned" and "what was actually verified" is weak.

3. **T3 governance rules (session-open CAP) only work for the first few turns.** After that, the AI is operating from recency and training defaults. The governance frame is background noise.

4. **Templates create the form of completeness, not the substance.** The §CC table gets filled with plausible-sounding content. But plausible is not verified.

---

## The Consolidation Path

The gap between "written correctly" and "works correctly" requires exactly one thing: **mechanical tests that simulate user behavior and block deployment if they fail.**

Not validators that check governance documents.
Not hooks that inject reminders.
Not checklists that get filled.

**Actual tests that execute the code paths users take.**

### For each artifact type, the completion test is:

**Pages:**
```
test: visit /page → no 500 error → interactive elements respond → form submits → redirect works
mechanism: E2E test suite (Playwright) wired to CI/CD
blocking: yes — deploy fails if any test fails
```

**Email templates:**
```
test: render template with sample data → HTML is valid → all links resolve → no broken images
mechanism: validate-email-template.mjs (check HTML structure + links)
blocking: advisory now, blocking at K=2
```

**Forms:**
```
test: fill all fields + submit → API returns 200 → success state shown
mechanism: API integration test + UI completion check
blocking: yes (API test blocks), advisory (UI check advises)
```

**API routes:**
```
test: POST/GET/PATCH/DELETE with valid payload → correct response → correct DB state
mechanism: existing __tests__/ in budget-planner
blocking: typecheck blocks
```

### What changes in the planning process:

Replace: "Done criterion: pnpm verify exit_code=0"
With: "Done criterion: [specific E2E test or manual test script that proves user can accomplish goal X]"

The done criterion must be **executable** and **user-behavior-oriented**, not governance-proxy-oriented.

### What changes in implementation:

Replace: "I created the file and it looks complete"
With: "I executed the done criterion test and it passed — here is the output"

The AI must SHOW the evidence, not declare it. This is the core of P-META-006 (RZF as evidence) applied to product completeness.

## Specific Protocol Changes Recommended

### 1. Mandatory user-journey test per PI item

Every PI item that creates user-facing functionality must include:
```yaml
user_journey_test: |
  Given: [user state]
  When: [user action]
  Then: [observable outcome — specific, not "it works"]
  Verified by: [how Sonnet proves this without a browser — API test, log output, or explicit note that Governor must verify]
```

### 2. Auto-audit on PostStop for implementation turns

When Sonnet reports completing a user-facing feature, the PostStop hook should:
1. Check if the feature has a user_journey_test in its PI item
2. If yes: require Sonnet to execute it and paste the output
3. If no: flag as ADVISORY "User-facing feature without a journey test"

### 3. Artifact-specific completion validators (build queue)

| Validator | Artifact | Priority | What it checks |
|---|---|---|---|
| validate-email-template.mjs | Email | HIGH | HTML structure, links, required fields |
| validate-form-complete.mjs | Forms | HIGH | Submit handler, validation, success/error states |
| validate-page-navigation.mjs | Pages | HIGH | All links resolve, no href="#" at deploy time |
| validate-chatbot-intents.mjs | Chatbots | MEDIUM | All intents have handlers, fallback exists |
| validate-landing-page.mjs | Landing pages | MEDIUM | CTA links, form submit, mobile check |

### 4. The single most impactful change

Add to every PostStop check:
> "If you just implemented something a user will interact with, describe in one sentence: what action can the user now take that they couldn't before? What happens step-by-step when they take that action? What do they see at the end?"

If the AI cannot answer this, the implementation is not complete — it passed governance checks but failed the user function test.

## Summary Table: What Is vs What Should Be

| Dimension | Current State | Should Be |
|---|---|---|
| Plan completeness | Template-filling | Executable specification with verifiable done criteria |
| Implementation completeness | "Validators pass" | "User can accomplish goal — evidence: [test output]" |
| Page completeness | "No syntax errors" | "All interactions work, all data flows, all states render" |
| Email completeness | "Template function exists" | "Email renders + links work + arrives in inbox" |
| Form completeness | "onSubmit exists" | "Data saved + success state shown + error handled" |
| Governance coupling | T3 (session injection, dilutes) | T2 (validator gates commit, permanent) |
| Satisfaction point | "This looks right" | "This test passed — here is the output" |

## What OPUS-2 Should Review

1. **PI item schema amendment:** Add `user_journey_test:` as a mandatory field for PI items with `status: implementing` that create user-facing features.

2. **PostStop hook:** Extend `post-stop-rzf-reminder.sh` to also require user-journey test output for implementation turns.

3. **Validator build order (PE-scored):**
   - `validate-form-complete.mjs` — HIGH PE (catches most common gap)
   - `validate-email-template.mjs` — HIGH PE (email is unverified after creation)
   - `validate-page-navigation.mjs` — MEDIUM PE (complements ui-completeness)

4. **Planning protocol:** Every SONNET DIRECTIVE for user-facing features must include a `user_journey_test:` block. This is a Rule 2 amendment.

5. **The hardest truth:** No amount of validators or hooks fully defeats the satisfaction-point default. The only reliable mechanism is **evidence-based done criteria** — forcing the AI to PRODUCE output that proves function, not DECLARE that function exists.
