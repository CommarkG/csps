# CSPS Phase 2 — Specific Package Index & Response Template

Version: V1
Status: Draft for External App Presentation

---

# 1. Purpose

This document defines the second-phase package sequence after an existing app completes Phase 1 absorption and internal planning.

Phase 2 introduces detailed packages gradually so the app can absorb the architecture in controlled modular batches.

---

# 2. Global Instruction

Every package is a suggestive optimization package, not an implementation command.

Before proposing changes, the receiving app should:

1. compare the package to what already exists
2. identify overlaps
3. identify conflicts
4. preserve working structures
5. identify safe extensions
6. suggest the smallest stable integration path
7. iterate at least three times before finalizing a plan

---

# 3. Package Sequence

## Package A — Dynamic Onboarding & Continuous Enrichment

Covers continuous onboarding, value before extraction, trust before depth, first input is partial, no interrogation, adaptive questioning, gentle challenge, delight moments, and enrichment triggers.

## Package B — Business Intelligence Layer

Covers onboarding as business intelligence for product configuration, profile understanding, user/tenant context, visibility, correction, and governed intelligence.

## Package C — Governance Constitution

Covers stable macro/adaptive micro, deterministic/probabilistic separation, confidence governance, convergence, user control, cold start, monetization, schema governance, and foundation-before-delight.

## Package D — Profile → Product Handoff

Covers Layer 1 identity/routing, Layer 2 intelligence, Layer 3 configuration contract, schema registry, feature flags, template prefills, bundle recommendations, promotion gates, audit logs, and versioning.

## Package E — UX/UI Adaptation & Screen Logic

Covers immutable UX shell, adaptive micro-containers, profile transparency, manual override console, role/context indicator, cold start UX, pause/resume, and question delivery.

## Package F — Monetization & Delight Governance

Covers delight before monetization, earned triggers, usage friction warnings, depth unlocks, team expansion, enterprise routing, and anti-manipulation rules.

## Package G — Implementation Sequencing

Covers foundation before delight, contracts before configuration, immutable shell before adaptive UI, confidence ledger before visible inference, shadow state before promotion, and auditability before AI configuration.

---

# 4. Recommended Delivery Method

Do not send all packages at once unless the receiving system is designed for large architectural review.

Preferred order:

1. Package A + Package B if conceptual capacity is high
2. Package C separately
3. Package D separately
4. Package E separately
5. Package F separately
6. Package G last

Each package should receive its own response before the next package is introduced.

---

# 5. Three-Pass Review for Every Package

## Pass 1 — Understanding

Explain what the package is trying to achieve.

## Pass 2 — Local Compatibility

Compare package to existing structures and identify overlaps, conflicts, strengths, missing foundations, and risks.

## Pass 3 — Optimized Integration Suggestion

Suggest the safest way to integrate or adapt the package while preserving stability and minimizing rebuild.

---

# 6. Standard Response Template

For each package, respond with:

1. Package understanding
2. Existing app mapping
3. Overlaps
4. Conflicts
5. What should be preserved
6. Gaps: critical / important / optional / future
7. Lowest-risk integration path
8. Suggested changes to the package
9. Required questions before implementation
10. Implementation readiness score from 1 to 5

---

# 7. Final Integration Rule

The receiving app should never treat the packages as replacement commands.

Preferred behavior:

- compare
- preserve
- challenge
- refine
- adapt
- optimize
- sequence carefully

After all packages are reviewed, produce a Local Integration Plan before implementation specifications begin.
