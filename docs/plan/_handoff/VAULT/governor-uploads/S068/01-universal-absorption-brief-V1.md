# CSPS Suggestive Integration Framework
## Phase 1 — Universal Absorption Brief

Version: V1
Status: External App Preparation Brief
Purpose: Help CSPS absorb the architecture safely before receiving detailed implementation packages.

---

# 1. Purpose

This brief is designed to help CSPS receive a refined architecture proposal without treating it as a forced implementation order.

The goal is not immediate implementation.

The goal is:

- absorb the direction
- compare it to what already exists
- preserve what works
- identify overlaps
- identify conflicts
- identify missing foundations
- prepare an internal integration plan
- iterate before suggesting implementation

This should be treated as a suggestive optimization framework.

---

# 2. Core Instruction to CSPS

Please do not implement yet.

Please do not rewrite existing architecture yet.

Please first inspect the current CSPS app and ask:

1. What already exists?
2. What already works?
3. What overlaps with this proposal?
4. What conflicts with this proposal?
5. What should be preserved?
6. What can be extended safely?
7. What should not be touched yet?
8. What is the smallest stable first step?

The best integration is not the one that copies the proposal exactly.

The best integration is the one that preserves CSPS strengths while safely adopting relevant principles.

---

# 3. Tone Requirement

All responses should be written as suggestions, not commands.

Preferred language:

- "Consider..."
- "It may be useful to..."
- "A safer path may be..."
- "Given the existing CSPS structure..."
- "Before changing this, inspect whether..."
- "This may already exist under another name..."
- "The lowest-risk integration path appears to be..."

Avoid:

- "Replace..."
- "Rebuild..."
- "Implement this directly..."
- "Remove the existing flow..."
- "Migrate immediately..."

CSPS should behave like an expert advisor optimizing an existing system, not an installer executing a fixed blueprint.

---

# 4. Universal CSPS Architecture DNA

## A. Suggestive Integration

New architecture should be optimized into CSPS, not forced onto CSPS.

## B. Extend Before Replace

Preserve useful existing systems. Prefer extension, wrapping, mapping, or governed enhancement before replacement.

## C. Stable Macro / Adaptive Micro

Core layouts, navigation, pricing, permissions, legal flows, and structural UX should remain stable. Personalization should happen inside bounded content areas.

## D. Deterministic vs Probabilistic Separation

Hard platform truth should be deterministic. AI inference should be probabilistic, scored, logged, correctable, and governed.

## E. Confidence Before Adaptation

Adaptive behavior should depend on confidence, fallback logic, and correction paths.

## F. User Control

Users should be able to correct, override, reset, or inspect important inferred assumptions.

## G. Business Intelligence for Configuration

Onboarding should gradually help CSPS understand the user, tenant, and use case in order to configure the right experience safely.

## H. Foundation Before Delight

Do not build impressive adaptive features before foundational contracts, state management, identity, auditability, and confidence governance exist.

---

# 5. Required Three-Pass Internal Review

CSPS should iterate at least three times before proposing implementation.

## Pass 1 — Understanding

Summarize what this framework is trying to achieve. Do not judge too quickly.

## Pass 2 — Compatibility

Compare the framework to the current CSPS architecture. Identify overlaps, conflicts, strengths, missing foundations, and risks.

## Pass 3 — Optimized Integration Plan

Suggest the safest integration path. Optimize for stability, low disruption, preservation of existing strengths, future scalability, and governance.

The third pass is the most important because first-pass responses are often reactive and second-pass responses often only detect conflicts.

---

# 6. Requested CSPS Response Format

## 1. Short Executive Understanding

## 2. Current CSPS Mapping

List existing systems that relate to this proposal.

## 3. Overlaps

What already exists under the same or different names?

## 4. Conflicts

What may conflict with current data models, UX, permissions, AI behavior, monetization, or technical constraints?

## 5. What Should Be Preserved

What current CSPS structures should not be disrupted?

## 6. Missing Foundations

Separate into critical, important, optional, and future opportunity.

## 7. Lowest-Risk First Step

Recommend the safest first action.

## 8. Three-Pass Internal Plan

Show the result of understanding, compatibility, and optimization passes.

## 9. Questions Before Receiving Detailed Packages

List what CSPS needs clarified before receiving deeper architecture packages.

---

# 7. Final Reminder

This is a preparation brief.

Please treat this as:

- a suggestion framework
- an optimization lens
- a compatibility assessment
- a planning request

not as:

- a rigid instruction set
- a replacement mandate
- an implementation command
- a rebuild order
