# 2. The Core Problem This Suite Solves

AI systems build UI by guessing. They guess what is needed, guess what the user wants, guess what comes next. The output is adjacent to the intent -- but not of the intent.
This happens because AI is given content without structure, style without logic, and goals without pipelines. The result is visually competent work that is structurally disconnected, contextually amnesiac, and impossible to govern at scale.

# 3. Governing Principles

These principles are not guidelines. They are structural rules. Every protocol in this suite enforces them. Every element at every level is accountable to them.

## Principle 1 -- Nothing Stands Alone

Every element must have a place in a pipeline and a corespine before it has a place on a page.
An element without a pipeline position is floating. A floating element is ungoverned. An ungoverned element cannot be built, audited, or trusted.

## Principle 2 -- Goal Requirement Is the Only Justification for Existence

Nothing in a pipeline exists because it seemed useful. Everything exists because the goal required it.
This applies not only to the pipeline as a whole -- it applies to every stage, every element, every transition, and every page. If existence cannot be traced to a goal requirement, existence is not justified.

## Principle 3 -- Existence Is Not Availability. Availability Is Not Actionability.

Every element must declare which of the four wiring states it is in -- always.
Wiring State
What It Means
What It Does NOT Mean
Defined
The element exists in the protocol with a populated backpack.
It is usable. It may have no live connections.
Wired
The element has live connections to upstream and downstream.
Those connections are current or accurate.
Reachable
The element's context is accessible at execution time.
The content is valid or current.
Current
The backpack reflects the actual live state of the system.
This is the only state that is truly actionable.

## Principle 4 -- Context Is More Significant Than Content

The same element carries different weight depending on where it sits, what it inherited, and what it is serving. Weight is situational, not fixed.
A title on a welcome page and a title on an error state page are not the same element. They are different expressions of the same component type, each with different weight, obligation, and behavior. The orchestrator assigns the variant. The element does not choose it.

## Principle 5 -- Inheritance Is Accumulated, Not Sequential

Every stage inherits from all stages before it -- not just the immediately preceding one. The chain is cumulative. Nothing drops out of the chain without explicit declaration.
An inheritance break -- where something from an earlier stage disappears from the chain without being declared consumed or resolved -- is a structural gap. It must be detected and resolved before implementation proceeds.

## Principle 6 -- Context Lives Inside the Element, Not Outside It

Every element carries its own context as an intrinsic property -- the Context Backpack. Elements do not depend on the system remembering to hand context to them.
This is the only mechanism that scales. As platform complexity grows, the number of relationships between elements grows exponentially. Re-prompting and re-injecting context is a patch. Intrinsic context is the architecture.

## Principle 7 -- Creation and Audit Are the Same Protocol Run in Opposite Directions

The audit protocol is the creation protocol in reverse. If they are not perfectly mirrored, drift between intent and output is inevitable.
Every creation decision must have a corresponding audit checkpoint. The audit checkpoint must check wiring state -- not just existence of the definition.

## Principle 8 -- Outcome Always Appears Near the End

In all step sequences, the outcome is what the sequence earns -- not where it starts. Every protocol in this suite presents things in intuitive human order: need first, outcome last.
