# 13-18. Vocabulary Additions to 1000 -- F3.1 Through F3.6

RESOLVED: F3.1 through F3.6   All six vocabulary gaps resolved. The following terms are added to Document 1000 with full three-depth definitions.
Term
CORE Definition
MEDIUM -- Good/Bad/Measured
FULL -- Hidden Principle
Zero Findings (Check)
The act of verifying what already exists in a declared scope before creating, detecting, or resolving anything new.
Good: check runs before every new action and finds existing elements. Bad: starting from scratch without checking -- redoing work, creating duplicates. Measured by: was the registry consulted?
Every platform's most expensive failure is rebuilding what already exists. Zero Findings is the structural practice that makes reuse the default and creation the exception.
Zero Findings (Protocol)
The mandatory discipline -- encoded in every protocol in this suite -- of checking what exists before acting. Not a one-time check. A continuous posture.
Good: every session, every pass, every agent invocation begins with this check. Bad: Zero Findings treated as optional or done once at session start only. Measured by: is there evidence of the check in every operation's audit trail?
A protocol that does not enforce Zero Findings is a protocol that will accumulate redundancy. Redundancy is not just waste -- it is a source of divergence, inconsistency, and platform drift.
Zero Findings (Skill)
SK-ORCH-0001 -- the declared, registered, depth-aware skill that executes the Zero Findings check. The operational form that makes the protocol executable by AI agents.
Good: invoked as the first action of every agent execution. Bad: agent checks existence informally without using the declared skill -- producing unauditable checks. Measured by: skill invocation log shows SK-ORCH-0001 as first entry in every agent audit trail.
A principle without an execution mechanism is an aspiration. SK-ORCH-0001 is what makes Zero Findings enforceable -- not just desirable.
Proof of Working
The evidence that a mechanism works continuously across a growing, diverse set of real conditions -- not just that it was completed or that tests passed.
Good: mechanism proven through GPOW four phases with real zero findings at each phase and backward propagation of all insights. Bad: proof declared based on checklist completion or test pass in controlled conditions. Measured by: GPOW closure declaration signed by Platform Governor.
Done based on effort or checklist is proximity to done. Proof of Working is actual done. The difference is not philosophical -- it determines whether the platform will hold at scale.
Done
The state declared only when Scale Proof is achieved -- after GPOW Phase 4 and Full Scope with zero findings across two consecutive expanded passes and Platform Governor closure signature.
Good: Done is traceable to a Governor-signed GPOW closure record. Bad: Done declared when effort was sufficient, when a checklist was completed, or when tests passed in the build environment. Measured by: GOV-[YEAR]-[SEQUENCE] reference in the GPOW closure record.
Done is not a feeling. It is a proof. And proof requires evidence from real conditions at real scale -- not from the environment designed to make things work.
Optimal Bundle
The precisely assembled set of platform elements at declared depth levels, scoped to achieve a declared goal within declared resource constraints, assembled in priority order.
Good: every element justified by the goal, every excluded element declared, resource-bounded, priority-ordered. Bad: maximum bundle assembled for safety, or minimum bundle assembled for speed, without goal-derivation. Measured by: can every included element be traced to the declared goal?
An Optimal Bundle is not the largest bundle that fits or the smallest that can proceed. It is the bundle that the goal requires -- no more, no less. The discipline of assembling it correctly is what makes the platform efficient rather than bloated.
GPOW
Abbreviation for Graduated Proof of Working Protocol. The four-phase methodology for proving mechanisms at scale -- Seed, Variance, Scale Confirmation, Full Scope.
Good: GPOW is used consistently as the abbreviation throughout the suite. Bad: expanding GPOW differently in different contexts. Measured by: every use of GPOW in the suite refers to Document 1090.
Formal abbreviations prevent semantic drift. An abbreviation without a formal declaration will be expanded differently by different readers and different AI sessions -- producing the vocabulary divergence that breaks context continuity.
Corespine Loop Engine
Deprecated alias for Loop Orchestrator. The original name used in early platform design conversations, now formally superseded.
Good: historical references to Corespine Loop Engine are understood as referring to the Loop Orchestrator (Document 1080). Bad: treating Corespine Loop Engine and Loop Orchestrator as different mechanisms.
Loop Orchestrator is the canonical term. Corespine Loop Engine is preserved as a deprecated alias to prevent confusion in sessions that reference early design conversations. Deprecated does not mean wrong -- it means superseded.
Blast Radius
Synonym for Ripple Effect (P1 in the Priority Engine). Both terms describe the downstream impact of an action across the platform's dependency graph.
Good: using either term to mean the same thing -- total downstream impact. Bad: treating Blast Radius as measuring direct impact only and Ripple Effect as measuring transitive impact. They are synonyms. Measured by: counting directly and transitively affected elements.
Two terms for the same concept create vocabulary split over time. Declaring them as synonyms prevents one from drifting to a different meaning. Ripple Effect is the preferred term in suite documents. Blast Radius is acceptable in conversation.

# 23. F4.6 -- Sub-Bundle Plan Constraint

RESOLVED: F4.6   Bundle Manifest sub_bundle_plan array is now constrained to maximum 5 sub-bundles.
Rationale: a bundle split into more than 5 sub-bundles is a bundle whose goal is too large for the available resources. The correct response is to reduce the goal scope -- not to create an unmanageable sub-bundle chain. Maximum 5 sub-bundles enforces goal-scoping discipline.

# 24. PE-1 -- Priority Score Threshold Derivation

RESOLVED: PE-1   Minimum threshold of 35 now has a declared derivation.
Derivation: The threshold of 35 represents the score produced by an action that achieves Standard ripple (P1=50), zero enablement (P2=0), zero gap resolution (P3=0), and Mostly Ready readiness (P4=60), at default weights (20% each).
(50x0.20) + (0x0.20) + (0x0.20) + (60x0.20) = 10 + 0 + 0 + 12 = 22 x P6 default 1.0 = 22.
Correction: re-deriving with all four parameters at their minimum non-zero values: P1=10 (local ripple), P2=0, P3=0, P4=20 (partially ready) = (10x0.20)+(0)+(0)+(20x0.20) = 2+4 = 6. This is too low to be meaningful. The 35 threshold represents: an action must achieve at least Standard ripple AND Mostly Ready to qualify for execution. This is a governance choice -- not a mathematical minimum. It is declared as such.

# 25. PE-2 -- P2 and P3 Interaction Cap

RESOLVED: PE-2   P2 and P3 stacking behavior is now declared.
P2 and P3 measure leverage from two directions -- future capability (P2) and current capability restoration (P3). An action can score high on both. When both P2 and P3 score above 70:
Combined Score Scenario
Rule
P2 > 70 AND P3 > 70
Cap the combined P2+P3 contribution at 80 points maximum (instead of potentially 200). Rationale: both are measuring downstream leverage. An action that appears maximally leveraged in both directions is likely being over-credited -- the same downstream effects are being counted twice.
P2 > 70 AND P3 <= 70
No cap. P2 contribution is uncapped.
P2  70
No cap. P3 contribution is uncapped.
