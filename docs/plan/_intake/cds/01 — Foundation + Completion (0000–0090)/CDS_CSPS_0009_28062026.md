# 1. How This Works

Document 0090 declares that every suite document must have a Learning Loop slot with eight declared fields. Rather than regenerating all 40 documents, this addendum declares those slots centrally for every document. Each document inherits its Learning Loop declaration from this addendum.
This addendum is the Learning Loop corespine for the suite. It gives every document a lineage to the Learning Loop -- and a declared set of triggers, vault feeds, and insight extraction points -- without requiring each document to be rewritten.

# 4. Optimizing ZF Cycles -- Insights from All Iterations

Running Insight Extraction across all 66 resolved findings and all ZF check events in this session produces the following ZF optimization insights:
ZF Optimization Insight
Evidence
Recommendation
ZF-SIMULATION is the most expensive check and should be reserved for expansion gates only
Every P-series finding was about expansion scope (moving from Sprint N to N+1, adding personas). None were about individual element definitions.
Reserve ZF-SIMULATION for: GPOW phase gates, sprint gates, scope expansion decisions. Do not run for routine operations -- use ZF-REGISTRY or ZF-SESSION instead.
ZF-REGISTRY has the highest frequency and lowest cost and should be automated
Every registry in the suite should enforce its own ZF-REGISTRY check -- a check that runs automatically when a new definition is attempted, before any human input is required.
All registries (Skill, Agent, Template, Element, Vocabulary, Bundle) should reject new entries that duplicate existing entries without explicit justification override.
ZF-SESSION is most valuable when it checks wiring states, not just existence
P2.1 (skills declared Wired before built) was invisible to existence-only checks. Wiring state verification caught it.
ZF-SESSION always checks wiring state of referenced elements, not just their existence. Stale entries that exist are more dangerous than missing entries.
ZF-PROPAGATION should check improvement version, not just coverage
F1.2 (backward propagation) revealed that forward propagation existed but was an older version than what backward propagation needed to carry.
ZF-PROPAGATION checks: has this target received this improvement OR a more recent version? Propagating older versions to targets with newer versions is a regression.
Running the wrong ZF type produces false confidence -- more dangerous than no ZF
All 24 P-series findings survived previous rounds precisely because the checks that ran (existence checks) were not designed to find structural gaps.
Declare ZF type before running. The ZF Type Selection Protocol in 0080 Section 4 is mandatory when ZF type is not already declared in the operation's protocol.
