# 1. Position in the System

What a skill is:  A platform primitive -- a single-capability, atomic execution unit that knows how to do one thing correctly, at declared depth levels, with governed input/output contracts.
What a skill is not:  A feature. A module. A service. A workflow. A skill is the smallest indivisible unit of governed capability in the platform.
Relationship to agents:  Skills are what agents invoke. An agent does not know how to do things -- it knows which skills to invoke, in what order, and with what context. Skills are atomic. Composition happens at the agent layer (0030) and orchestrator layer (3000).
Relationship to elements:  A UI element (1050) has a visual expression and a pipeline role. A skill has a capability contract and an execution profile. They are parallel primitives -- elements govern what is seen and acted on. Skills govern what happens when actions are taken.
A skill is defined as atomic at the definition layer. Composition is the orchestrator's responsibility -- not the skill's. A skill that tries to do two things is two skills that have not been separated yet.
ZERO FINDINGS MANDATORY   Before defining any new skill -- check the Skill Registry. A capability that already exists as a validated skill must be reused -- not redefined. A new skill definition requires explicit justification that no existing skill covers this capability.

# 2. Skill Definition -- What Makes a Skill Governed

A skill is governed when it can answer five questions without ambiguity. An ungoverned skill -- one that cannot answer all five -- is a liability. It cannot be safely invoked by an agent, cannot be audited, and cannot be depth-routed by the orchestrator.
Q1 -- What is the single thing I do?
One capability. One verb. Validate an inheritance chain. Extract context weight from a backpack. Parse a pipeline stage definition. Generate a gap detection report. One thing -- stated as a verb phrase, not a noun category.

Q2 -- What is my input contract?
Exactly what the skill receives. Named, typed, and depth-declared. A skill that accepts vague or untyped input cannot be safely composed by an agent or bundled by the orchestrator.
Q3 -- What is my output contract?
Exactly what the skill produces. Named, typed, and wiring-state-declared. The output wiring state cannot exceed the input wiring state. A skill that receives Defined inputs cannot produce Current outputs.
Output wiring state ceiling rule: a skill's output can never exceed the wiring state of its lowest-quality input. Garbage in, garbage out is not a metaphor -- it is a wiring state constraint.
Q4 -- What are my failure modes?
Every skill has declared failure modes. Not error handling code -- declared behavioral outcomes when the skill cannot complete its function. Three categories: graceful degradation, partial output with declaration, or halt with reason.
Q5 -- What depth level am I operating at?
Every skill invocation declares its operating depth -- Core, Medium, or Full. The depth determines which inputs are required, which outputs are produced, and which failure modes are active. A skill invoked at Core depth with Full-depth inputs is a depth mismatch -- blocked by the Depth Router.

# 5. Atomic at Definition -- Composable at Orchestration

This is the governing architectural decision for skills in CSPS. It resolves the tension between governance and power.
Principle
What It Means
Why It Matters
Atomic at definition
Every skill is defined to do one thing. Its input contract, output contract, and failure modes describe one capability only. No skill may have a branching purpose at definition time.
Atomic skills are fully auditable. Their behavior is predictable. Their failure modes are exhaustive. Composed behavior that fails can be traced to the specific skill that failed.
Composable at orchestration
The orchestrator and agents compose skills into sequences. A pipeline validation sequence might invoke three atomic skills in order. Each skill is still atomic -- the composition is the agent's responsibility.
Composition at the orchestration layer means skills can be recomposed for different purposes without changing their definition. The same gap detection skill serves the wizard, the orchestrator, and the audit loop.
No skill-to-skill direct calls
Skills do not invoke other skills. An agent invokes skills in sequence. This prevents hidden dependency chains that bypass the orchestrator's governance.
Hidden skill-to-skill calls bypass depth routing, bundle assembly, and gap monitoring. The orchestrator cannot govern what it cannot see.
A skill that calls another skill is an agent that has not been declared. Declare it as an agent in 0030 and govern it correctly -- do not hide composition inside a skill definition.

# 6. The Skill Registry

Every skill defined using this standard is registered in the Skill Registry. The registry is the Zero Findings check target for all skill invocations and all new skill definitions.
ZERO FINDINGS MANDATORY   The Skill Registry is the first check before any skill is defined or invoked. A capability that already exists as a registered skill must be reused. Duplicate skill definitions are a governance violation -- they create parallel ungoverned implementations of the same capability.
