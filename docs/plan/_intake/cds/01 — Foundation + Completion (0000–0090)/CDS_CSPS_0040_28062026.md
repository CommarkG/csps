# 1. What the Priority Engine Is

Definition:  The mechanism that determines what gets done, when it gets done, and in what order -- across the entire platform and within every individual session. Not a ranking list. A living decision system that evaluates candidates against six weighted parameters and produces a governed execution order.
Scope:  Platform-wide: governs the order of pipeline execution, agent invocation, skill bundling, and loop iteration. Session-level: governs which elements are built first, which gaps are resolved first, which depth levels are targeted first.
Personal configuration:  Every user configures parameter weights. No default configuration is applied without explicit user consent. The engine is personalized -- not standardized.
The Priority Engine does not decide what to do. It decides what to do FIRST. Everything eventually gets done -- the engine governs the order and the packaging, not the scope.
ZERO FINDINGS MANDATORY   Before any priority assessment -- check what has already been prioritized and executed in previous cycles. An action that was already executed does not re-enter the priority queue. An action that was deprioritized in a previous cycle must carry its deferral reason forward.

# 2. The Six Priority Parameters

Every candidate action is scored against all six parameters. The weighted sum determines execution order. Parameters are not binary -- they are scored on a declared scale and weighted by user configuration.

## P1 -- Ripple Effect (Blast Radius)

PRIORITY PRINCIPLE   The larger the downstream impact of executing this action across the platform's dependency graph -- the higher it ranks. Ripple effect is measured by counting how many elements, pipelines, corespines, and sessions are directly or transitively affected by this action.

## P2 -- Enablement Factor

PRIORITY PRINCIPLE   How many dormant, blocked, or partially functional things does this action bring to life? Actions that unlock other actions multiply their value beyond their direct output. This is the key-that-opens-many-doors parameter.
An action with a low ripple effect but a high enablement factor ranks higher than its ripple score alone would suggest. Building the infrastructure that makes ten future actions possible is worth more than executing one action directly.

## P3 -- Gap Resolution Value

PRIORITY PRINCIPLE   How many existing things work significantly better once this gap is closed? Not creating new capability -- restoring blocked capability that already exists but cannot function. Resolving a gap that was holding back ten elements is worth more than creating one new element.

## P4 -- Readiness Factor

PRIORITY PRINCIPLE   Given two actions with similar combined scores on P1-P3 -- prefer the one that is simpler, more certain, and available now over the one that is complex, unknown, or potentially damaging. Progress on available paths builds infrastructure maturity that makes complex actions tractable later.
This parameter prevents the platform from stalling on complexity. It encodes the insight that complexity is often not intrinsic to a problem -- it is a symptom of insufficient readiness. Choosing available progress over blocked ambition is not settling. It is strategic sequencing.

READINESS THRESHOLD   READINESS THRESHOLD -- the governing constraint on P4: If an action has been at 'Not Ready' or 'Partially Ready' for two consecutive cycles AND it has a P1 score of Major Ripple or above AND it is blocking other high-value actions -- it must be escalated to Platform Governor for a forced resolution decision. P4 cannot be used indefinitely to defer critical work.

## P5 -- Resource Reality

PRIORITY PRINCIPLE   Token window availability, human time available, session length constraints -- all actively checked and validated through direct human input before priority scoring begins. Not assumed. Not defaulted. Asked. Actions that exceed available resources are not ranked -- they are deferred to a session where resources are sufficient.
This parameter closes the false assumption loop. An AI that plans beyond available resources is not being helpful -- it is creating debt. Resource Reality is the parameter that grounds the priority engine in what is actually possible right now.

False resource assumptions are the single largest source of incomplete sessions. An AI that begins a Full-depth session without confirming token availability will produce truncated outputs that look complete but are not. Ask first. Always.

## P6 -- Personal Weight Configuration

PRIORITY PRINCIPLE   Every user configures the relative weight of each parameter. The priority engine produces different execution orders for different users -- not because the parameters change, but because their relative importance differs by context, role, and working style.
Configuration Element
Definition
Default if Not Set

20% -- standard weight

20% -- standard weight
P3 Weight (Gap Resolution)
How much does the user value restoring existing function vs. creating new capability?

How much does the user value certainty and simplicity vs. ambition and risk?

Weight configuration is stored in the user's session profile and referenced by the Priority Engine at the start of every session. It is not re-entered each time. It persists until explicitly changed.

# 3. Priority Scoring -- The Calculation

Priority score is a weighted sum of the six parameter scores. The formula is applied to every candidate action before execution order is determined.
Formula Element
Content
Priority Score
(P1 score x P1 weight) + (P2 score x P2 weight) + (P3 score x P3 weight) + (P4 score x P4 weight) + (P5 check passed? x P5 weight) + P6 personal adjustments
P5 special handling
P5 is a gate, not a score. If P5 check fails (resources insufficient), the action is deferred regardless of its combined P1-P4 score. P5 does not add to the score -- it removes ineligible candidates.
Score range
0-100. Above minimum threshold: enters execution queue in score order. Below minimum: parked with reason.
Tie-breaking rule
When two actions have identical scores: P4 (Readiness) is the tiebreaker. The simpler, more certain action executes first.
Re-scoring trigger
Platform state changes -- a gap is resolved, a new skill becomes available, a dependency wiring state changes -- trigger re-scoring of all parked and queued actions.

# 4. Mini Priority Engines -- Session-Level Instances

The Platform Priority Engine governs platform-wide execution order across cycles. Every session also runs its own Mini Priority Engine -- a session-scoped instance that governs execution order within that session, using the same six parameters but scoped to session-available actions only.
Dimension
Platform Priority Engine
Mini Priority Engine
Scope
All platform actions across all cycles
Actions available within current session only
Time horizon
Multi-cycle -- plans across build cycles
Single session -- plans within available resources
Weight configuration
User's persistent profile
Same profile -- but P5 (Resource Reality) weight is elevated to 30% minimum for session-level scoring
Re-scoring frequency
On platform state change events
After every action completion within the session
Output
Platform execution roadmap
Session execution sequence
Relationship
Mini Engine inherits from Platform Engine -- session actions must be drawn from the Platform Engine's queue
Cannot execute actions not in Platform Engine's queue -- Mini Engine refines order, does not create new priorities
PRIORITY PRINCIPLE   The Mini Priority Engine is the Platform Priority Engine at session depth. It does not contradict the platform-level order -- it executes the highest-priority platform actions that are achievable within current session resources. It is the bridge between strategic priority and tactical execution.
