# 1. The Bundling Philosophy -- Why It Is a First-Class Principle

Bundling is not a technical detail inside the Bundling Engine (3020). It is a governing philosophy that shapes every decision about what gets assembled, what gets executed, and what gets deferred across the entire platform.
BUNDLING PRINCIPLE   Always ask: what is the optimal bundle for this goal? Not the maximum bundle. Not the minimum bundle. The optimal bundle -- the precise set of elements, at the precise depth levels, needed to achieve the declared goal within available resources.
The Bundling Philosophy operationalizes three principles simultaneously:
Principle
What It Means in Practice
Whole units, not fragments
Elements, pipelines, corespines, templates, and pages are consumed as validated whole units at their declared depth level. Partial consumption without explicit declaration of what is excluded and why is a governance violation.
Depth-matched assembly
Every element in a bundle is consumed at the depth level appropriate to its role in the current goal. No element is over-loaded or under-loaded without documented reason.
Priority-ordered packaging
Elements are added to the bundle in priority order from the Priority Engine (0040). The highest-priority actions are bundled first. If resources run out, the lowest-priority elements are excluded -- not the highest.

# 2. What an Optimal Bundle Is

Definition:  An Optimal Bundle is a precisely assembled set of platform elements -- skills, agents, pipelines, corespines, pages, templates, elements -- at declared depth levels, scoped to achieve a declared goal within declared resource constraints, assembled in priority order.
BUNDLING PRINCIPLE   An Optimal Bundle is not the largest bundle that fits in available resources. It is the smallest bundle that fully achieves the declared goal. Every element in the bundle justifies its presence. Every element excluded from the bundle has a declared reason for exclusion.

## 2.1 The Four Bundle Properties

Property
Definition
What Violates It
Goal-derived
Every element in the bundle is present because the declared goal requires it. Elements added because they might be useful are not in an Optimal Bundle.
Adding elements speculatively -- 'we might need this later.' Speculation has no place in a bundle. If it is needed, it belongs. If not, it is excluded.
Depth-matched
Every element is at the correct depth level for its role. No element is at Full depth when Core is sufficient. No element is at Core depth when Medium is required.
Defaulting all elements to Full depth because it feels safer. Full depth is maximum load. Maximum load is not optimal -- it is the failure mode Optimal Bundling prevents.
Resource-bounded
The bundle fits within declared available resources -- token window, session time, human attention. If it does not fit, it is split into sub-bundles or deferred items are explicitly declared.
Assembling a bundle that exceeds available resources and planning to 'see how far we get.' Incomplete bundle execution produces partial outputs that look complete but are not.
Priority-ordered
Elements are assembled and executed in Priority Engine order. The bundle executes highest-priority actions first. If the session ends before completion, the most valuable work was done.
Executing elements in discovery order or convenience order. Arbitrary ordering means the session may run out of resources before the most important work is done.

# 4. Whole Units -- The Non-Negotiable Rule

Every element consumed in a bundle is consumed as a complete unit at its declared depth level. Partial consumption -- consuming some slots of a backpack but not others -- is not permitted without explicit declaration.
A pipeline stage consumed at Medium depth is consumed with ALL Medium-depth backpack slots. Not nine out of thirteen. All thirteen. If a slot cannot be populated, the element is not at Medium depth -- it is at Core depth and must be declared as such.
Whole Unit Rule
What It Prevents
How Enforced
All depth-level slots must be populated before an element is consumed at that depth
Partial backpacks that look complete but are missing critical slots -- creating false confidence in element quality
Bundling Engine (3020) validates slot completeness before adding element to bundle
An element cannot be split across depth levels within a single bundle
An element consumed at Core for some purposes and Medium for others within the same session -- creating context inconsistency
Depth Router (3010) assigns one depth level per element per session -- not per slot
Excluded elements must be declared
Silent exclusion -- an element omitted from a bundle without acknowledgment, creating gaps that are not detected
Bundle manifest includes both included elements AND explicitly excluded elements with reasons
BUNDLING PRINCIPLE   A bundle that silently excludes a required element is not an Optimal Bundle -- it is a gap waiting to be discovered at runtime. The bundle manifest is the declaration of what is in, what is out, and why. It is not generated after assembly -- it is the assembly plan.

# 5. The Bundle Manifest

Every bundle has a Bundle Manifest -- the pre-execution plan that declares all included elements, all excluded elements, depth assignments, resource allocation, and priority order. The manifest is produced before execution begins and approved before the first action is taken.
Manifest Field
Content
Rule
Bundle ID
Unique identifier -- BND-[SESSION-TYPE]-[DATE]-[SEQUENCE]
Generated at bundle creation. Never reused.
Bundle Type
One of the six declared bundle types
Must match session goal declared at session start
Declared Goal
Single sentence -- what this bundle achieves
Traceable to Pipeline Q5 or session goal. If not traceable -- bundle is not started.

Token window available, human time available, session depth sustainable
Must be confirmed by human user -- not assumed. P5 check must pass before manifest is finalized.
Priority Order
Ranked list of all actions in this bundle -- highest Priority Score first

Included Elements
Every element in the bundle -- ID, depth level, role in achieving bundle goal
Every inclusion justified. No speculative elements.
Excluded Elements
Every element considered but excluded -- with reason for exclusion
Silent exclusion is not permitted. If an element was considered, it appears here.
Sub-bundle Plan
If full bundle exceeds resources -- declared split into sub-bundles with order
Sub-bundle order is priority-governed. Most valuable sub-bundle executes first.
Completion Criteria
What done looks like for this bundle -- the observable signal
Must match declared goal. If goal and completion criteria diverge -- bundle is not started.

# 6. Bundling and the Priority Engine -- The Integration

Bundling and priority are inseparable. The Priority Engine determines order. Bundling determines packaging. Together they ensure that the most valuable work is done first, in the most resource-efficient way, producing outputs that are complete at their declared scope.
Priority Engine Output
Bundling Response
Ranked action list from Platform Priority Engine
Bundling Engine assembles actions into a bundle in priority order -- highest first
Resource Reality constraint from P5
Bundle is scoped to available resources -- lower-priority actions are deferred, not abandoned
Readiness scores from P4
Only Ready or Mostly Ready elements enter the bundle -- Partially Ready elements are noted in excluded list with readiness gap declaration
Re-scoring trigger after action completion
Bundle manifest is updated after each completed action -- next action is re-confirmed as still highest priority before execution
Mini Priority Engine session scope
Session bundle is assembled from Mini Priority Engine output -- platform-wide actions not achievable in this session are not in the bundle
BUNDLING PRINCIPLE   The bundle is the physical expression of the priority order. Priority without bundling is a ranked list. Bundling without priority is a random collection. Together they are the execution plan that turns platform strategy into governed, resource-efficient action.
