# 1. The Core Insight -- ZF Is a Family, Not a Single Check

Zero Findings appears throughout the suite as a single mandatory principle. But examining how it is used reveals four structurally different behaviors that share one root:
The root: check what already exists before acting. The branches: what counts as 'existing,' what scope is checked, at what depth, and what constitutes a clean result -- all differ by context.
Running a Registry ZF when a Simulation ZF is needed is as wrong as running no ZF at all. The wrong check type produces false confidence -- the check passes, the actor proceeds, and the gap that should have been found is found later at higher cost.
ZF Type
Root Behavior
Branch Behavior
What Goes Wrong With Wrong Type
Registry ZF

Running Registry ZF when Simulation ZF is needed: registry shows no duplicates but structural gaps are invisible to registry check
Session ZF

Queries current session state -- what was built, what was resolved, what is in context

Check before propagating
Queries Dynamic Completion vault for existing propagation coverage of the target finding
Running Propagation ZF when Session ZF is needed: vault shows coverage but session state is stale -- propagation runs on outdated context

# 2. The Four ZF Types -- Full Definitions


## ZF-REGISTRY -- Existence Before Definition

ZF-REGISTRY   Before defining any new element -- check the relevant registry. A definition that already exists must be reused. A new definition requires explicit justification that no existing entry covers this element's role.
Property
Definition
Trigger
Any new definition is about to be created: skill, agent, pipeline, corespine, page, element, template, vocabulary term
Scope
The specific registry relevant to the element type being defined
Depth
CORE -- existence check only. Wiring state check is optional at this level.
Check Question
Does an entry already exist that serves this role?
Clean Result
No matching entry found -- new definition is justified. OR: matching entry found -- it is reused, not redefined.
Dirty Result
Matching entry found but a new definition is created anyway -- this is a governance violation.
Executor
SK-ORCH-0001 with check_type = existence
When to Upgrade
If the existence check reveals an entry that looks related but the actor is uncertain whether it covers the new case -- upgrade to ZF-SESSION to get broader context.

## ZF-SESSION -- Current State Before Acting

ZF-SESSION   At the start of every session -- check what the current session inherits from previous sessions. What was built? What was resolved? What is still open? What has changed in the platform since the last session?
Property
Definition
Trigger
Session start. Also triggered by: loop cycle transition, sprint gate check, agent invocation start.
Scope
Current loop state, current priority queue, current wiring states of elements involved in this session's scope.
Depth
MEDIUM -- existence plus wiring state verification. Stale entries are flagged.
Check Question
Is the current platform state accurately represented in this session's starting context?
Clean Result
Loop state is Current. Priority queue reflects current platform state. All referenced elements are at their declared wiring states.
Dirty Result
Loop state is stale (previous cycle exit state not updated). Priority queue has actions that were completed but not removed. Referenced elements' wiring states have changed since they were last checked.
Executor
SK-ORCH-0001 with check_type = currency -- checks wiring states of all elements in scope
When to Upgrade
If session state reveals structural gaps (not just stale state) -- upgrade to ZF-SIMULATION.

## ZF-SIMULATION -- Structural Coherence Before Expansion

ZF-SIMULATION   Before expanding to the next GPOW phase, the next sprint, or the next scope level -- run all six gap types against the current scope at the appropriate depth. This is the most comprehensive ZF check and is used sparingly.
Property
Definition
Trigger
GPOW phase gate. Sprint gate. Simulation Agent expansion decision. After any major structural change (new corespine declared, new pipeline defined, new agent registered).
Scope
All elements in the current GPOW scope -- documents, pipelines, corespines, pages, elements, agents, skills.
Depth
FULL for gap types that require it (T6 always FULL), MEDIUM for others. Depth determined by gap type depth profiles from 1030 V2.
Check Question
Are there structural gaps in the declared scope that would cause failures at the next scale level?
Clean Result
All six gap types return zero findings for the declared scope. Gate opens.
Dirty Result
One or more gap types return findings. Gate does not open. Findings are resolved before expansion.
Executor
Simulation Agent (0060) -- six personas running gap detection skills
When to Downgrade
If the full simulation is disproportionate to the change being validated -- downgrade to ZF-SESSION for minor state changes, ZF-REGISTRY for simple new definitions.

## ZF-PROPAGATION -- Coverage Before Propagating

ZF-PROPAGATION   Before propagating an improvement or fix -- check whether it has already been propagated to the target. Propagating what is already current is waste. Worse: it can overwrite more recent improvements with older ones.
Property
Definition
Trigger
Before any Dynamic Completion propagation action. Before any backward propagation step in the GPOW Insight Registry.
Scope
The specific propagation target -- the element, document, or session that is about to receive the improvement.
Depth
MEDIUM -- check current improvement state of target. Verify wiring state.
Check Question
Has this target already received this improvement (or a more recent version of it)?
Clean Result
Target has not received this improvement. Propagation proceeds.
Dirty Result
Target already has this improvement at equal or higher quality. Propagation is skipped. This is a clean result -- not a problem.
Executor
SK-ORCH-0001 with check_type = propagation_coverage -- checks vault entry against target element's improvement history
When to Upgrade
If propagation check reveals the target is at lower wiring state than expected -- upgrade to ZF-SESSION to understand why.

# 3. The ZF Corespine -- Root and Branches

The four ZF types share a root and form a corespine. The root is the platform principle: existence before action. The branches are the four specific behaviors, each with its own scope, depth, trigger, and executor.
Corespine Element
Value
Corespine ID
CS-ZF-UNIVERSAL
Corespine Name
Zero Findings Universal Corespine
Root Goal
Ensure that what already exists is consulted before any creation, expansion, propagation, or action
Root Principle
Check before acting. Always. The cost of checking is always less than the cost of missing.
Branch 1
ZF-REGISTRY -- existence before definition
Branch 2
ZF-SESSION -- current state before acting
Branch 3
ZF-SIMULATION -- structural coherence before expansion
Branch 4
ZF-PROPAGATION -- coverage before propagating
Inherited By
Every protocol, every wizard, every orchestrator component, every agent in the suite
The corespine gives ZF its lineage. An agent that receives the instruction 'run Zero Findings' must now ask: which type? The answer comes from context -- what is about to happen? That context determines which branch of the ZF corespine applies.

# 5. Universal Pass Elements -- What Every ZF Check Always Does

Regardless of ZF type, every ZF check always includes these universal elements. These are the root behaviors that all four branches inherit.
Universal Element
Definition
Timestamp
Every ZF check records when it ran. No undated ZF check is valid.
Scope declaration
Every ZF check declares what it checked. An undeclared scope cannot be verified.
Result declaration
Every ZF check declares its result: Clean / Dirty / Upgraded (type was changed mid-check) / Inconclusive (scope unclear -- return to actor).
Executor declaration
Which skill (SK-ORCH-0001 variant) ran the check. Informal ZF checks -- not run by a declared skill -- are not governed ZF checks.
Audit trail entry
Every ZF check produces an audit trail entry in the invoking agent's or session's audit log.
Learning Loop feed
Every ZF check result is an input to the Learning Loop. What was found? What type of check found it? See 0090.

# 6. ZF Optimization -- Insights from Iteration Analysis

Examining all ZF failures identified across the 66 resolved findings produces four optimization rules.
Optimization Rule
Finding Pattern That Produced It
Never run ZF-REGISTRY when ZF-SIMULATION is the correct type. A clean registry does not mean a coherent structure.
P1.3 (persona output format), P7.3 (Agent Registry schema) -- registries existed but structures were incoherent
ZF-SESSION must verify wiring states, not just existence. Stale entries that exist are as dangerous as missing entries.
P2.1 (skills declared Wired before built), P2.3 (Sprint 1 P5 skill reference) -- elements existed at wrong wiring states
ZF-SIMULATION must run before every scope expansion, not just before major releases. Expansion is the moment of maximum risk.
All 24 P-series findings: none were found inside individual elements. All were found at expansion boundaries.
ZF-PROPAGATION must check improvement version, not just existence. Propagating an older version to a target that already has a newer version is a regression.
F1.2 (backward propagation not wired) -- propagation was forward-only, creating version divergence between early and late elements

# 8. Audit Mirror

Audit Question

Does every ZF audit trail entry declare which of the four types was run?
Universal elements present
Does every ZF audit trail entry show timestamp, scope, result, executor, and audit trail entry?

Does the declared ZF type match the context: registry check for new definitions, session check for session starts, simulation for expansion, propagation for propagation?
Learning Loop fed
