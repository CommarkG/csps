# 1. The Governing Principle

RATIFICATION BLOCK   Nothing in this platform is activated without ratification. Ratification is not a ceremony -- it is a state. A DRAFT or PENDING element does not exist for platform purposes. It is a proposal. Activation requires a RATIFIED state, achieved through explicit Platform Governor approval.
This is Option B -- ratification as an independent orthogonal status separate from wiring state. An element can be technically perfect (wiring state = Current) but not ratified (ratification state = PENDING). Both must be true for activation. Neither alone is sufficient.

# 2. The Ratification States

State
Definition
Transitions
PENDING
Element has been declared but not yet reviewed by the Platform Governor. Default state for all new declarations.
-> APPROVED (Governor approves) | -> HELD (Governor requests changes) | -> REVOKED (Governor rejects entirely)
APPROVED
Platform Governor has reviewed and formally approved this element for activation. Recorded as GOV-[YEAR]-[SEQUENCE].
-> HELD (Governor suspends approval pending re-review) | -> REVOKED (Governor withdraws approval)
HELD
Governor has identified concerns. Element cannot be activated. Changes required before re-submission.
-> PENDING (changes made, re-submitted) | -> REVOKED
REVOKED
Governor has withdrawn approval. Element cannot be used. Dependent elements must be reviewed.
-> No forward transition. A revoked element must be redesigned and re-submitted as a new declaration.

# 4. The Dependency Grid

The Ratification Block creates a dependency grid -- not just at the starting point but ongoing. This grid governs both how the system builds itself and how it builds outward for external users and SaaS solutions.
Nothing can be activated that depends on an unratified element. This rule propagates through the entire dependency chain. If CS-GOV-001 is not ratified, nothing that depends on it can be ratified -- regardless of how well built it is.
Grid Rule
Definition
Enforcement
Ratification propagates upward
A dependent element cannot be ratified until all its declared dependencies are APPROVED.
Ratification submission is automatically rejected if any dependency is not APPROVED. Governor cannot override this -- it is structural.
Revocation propagates downward
When a ratified element is REVOKED, all elements that depend on it are automatically moved to HELD.
Dynamic Completion vault receives REVOKED status and creates propagation entries for all dependents.
Changes require re-ratification
Any change to a ratified element requires re-ratification. The element returns to PENDING and all dependents return to HELD.
Version tracking in the ratification record. Changed element has new GOV-[YEAR]-[SEQUENCE].
The grid is ongoing
New elements added to the platform are validated against the current dependency grid. A new element cannot reference an unratified element.
Every new declaration includes a dependency validation step that checks ratification states.
External users inherit the grid
When the platform builds SaaS solutions for external users, those solutions inherit the dependency grid. An external solution cannot activate capabilities based on unratified corespines.
External solution deployment includes ratification state verification for all activated corespines.

# 5. The Ratification Ceremony

Every ratification is a structured event -- not an informal approval. This is the ceremony that converts PENDING to APPROVED.
Ceremony Step
Action
Document
1 -- Submission
Element owner submits the element for ratification. Submission includes: element declaration, dependency list with current ratification states, justification for creation (what lineage gap does this fill?).
Submission record: RAT-SUBM-[ELEMENT-ID]-[DATE]
2 -- Dependency verification
Automatic check: are all declared dependencies APPROVED? If no -- submission rejected with list of unratified dependencies.
Rejection record or dependency confirmation
3 -- Governor review
Platform Governor reviews: purpose (does this fill a real lineage gap?), correctness (is the root, trunk, and branch structure sound?), dependency (is the dependency chain correct?), conflicts (does this conflict with existing ratified elements?).
Review notes: RAT-REVIEW-[ELEMENT-ID]-[DATE]
4 -- Decision
Governor decides: APPROVED | HELD (with specific changes required) | REVOKED (with reason). HELD requires a re-submission with declared changes. REVOKED means redesign.
GOV-[YEAR]-[SEQUENCE]
5 -- Registry update
Element status updated to APPROVED. Dependent elements notified. Dynamic Completion vault entry created.
Registry update + DC vault entry
6 -- Activation
Element wiring state progresses normally. Ratification state = APPROVED is the green light for implementation to begin.
Implementation sprint scheduled

# 6. The Corespiral Build Sequence -- Ratification Embedded

The Corespiral Implementation Protocol (0070) describes 8 sprints. Each sprint is governed by the Ratification Block. Here is how ratification is woven into the corespiral from the first cycle:
Sprint
Ratification Actions
Sprint 0 (Pre-Build)
Ratify CS-CORE-001, CS-CORE-002, CS-CORE-003 (this document and 0100). Ratify CS-GOV-001 (this document). No sprint 1 begins until these four are APPROVED.
Sprint 1 (Kernel)
Ratification state checking implemented as a function. Every component in the kernel declares its ratification dependencies. Priority Engine includes ratification state as a gate (unratified elements are not in the execution queue regardless of priority score).
Sprint 2 (Simulation)
Simulation Agent includes ratification state verification in ZF-REGISTRY checks. A simulation finding that discovers an unratified dependency is a Gap Type 1 (Orphan -- no ratified ancestry).
Sprint 3 (Dynamic Completion)
Dynamic Completion vault receives REVOKED and HELD status changes as triggers. Propagation analysis runs for all affected dependents.
Sprints 4-8
Every new corespine, protocol, or governing element requires ratification before the sprint that implements it. Ratification ceremonies are scheduled before their sprint, not during.
