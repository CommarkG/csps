# 1. CS-AI-001 -- AI Behavior Corespine

CS-ID:  CS-AI-001
Tags:  AI | BEHAVIOR | TRIGGER | REACTIVE | STRONG-ABILITY | WEAK-ABILITY | DEFAULT | PATTERN
Root Goal:  Govern the complete behavioral profile of AI systems operating within the platform -- including their default capabilities, their default failure modes, their hardcoded triggers, and their reactive patterns
Root Principle:  AI behavior is not emergent -- it is governed. Every AI operating in this platform has a declared behavioral profile. Ungoverned AI behavior is the primary source of platform drift.
AI PRINCIPLE   The most important and most ignored corespine in the suite. AI systems have hardcoded behaviors that activate regardless of user or platform intent. Knowing these behaviors -- their triggers, patterns, strengths, and weaknesses -- is the prerequisite for governing AI effectively.
Layer
Elements
Rule
Root
AI behavioral declaration
Every AI system that operates in this platform has a declared behavioral profile. No AI without a profile. No undeclared behavior.
Trunk -- Four behavior categories
Triggers, Reactive Patterns, Default Strong Abilities, Default Weak Abilities
All four must be declared for each AI system. Missing declarations are ratification gaps.
Branch 1 -- Triggers
Words, phrases, and patterns that activate hardcoded AI reactions regardless of user intent
Trigger mapping: input pattern -> activated reaction. Triggers are detected before instruction processing.
Branch 2 -- Reactive Patterns
Default behaviors that activate when triggers fire -- independent of platform governance
Pattern mapping: trigger -> reaction behavior. Understanding reactive patterns enables interception before damage.
Branch 3 -- Default Strong Abilities
What the AI does exceptionally well by default -- capabilities that are reliable and that platform governance should leverage
Strong ability leverage: where to use AI without heavy governance scaffolding
Branch 4 -- Default Weak Abilities
What the AI does poorly by default -- capabilities that require maximum governance scaffolding to produce correct outputs
Weak ability compensation: where to apply maximum context, validation, and ZF checking

## 1.3 Known Trigger Patterns -- For Claude Sonnet 4.6

Trigger Pattern
Activated Reaction
Platform Interception
'Make this better' / 'improve this'
Expands scope, adds content, increases complexity -- regardless of whether improvement was needed or scope was appropriate
Require specific improvement criteria before using this phrase. Replace with: 'Improve [specific aspect] within [declared scope].'
'Clean up' / 'simplify'
Removes content that appears redundant -- including content that was intentionally placed for governance reasons
Never use without declaring what must be preserved. Use: 'Simplify while preserving [specific governance elements].'
Long conversation context
Drift toward earlier conversation themes, compression of recent instructions
Explicit context anchors: 'As declared in [document ID]...' ZF-SESSION at session start.
Praise or confirmation ('great', 'perfect')
Reduces critical analysis, increases agreement -- even when disagreement would be appropriate
Avoid confirmatory language before critical review passes. Use neutral acknowledgment.
Large scope requests
Produces comprehensive-looking outputs that prioritize coverage over correctness
Scope declarations with explicit boundaries. Depth declarations. Maximum sub-bundle count (5).
Ambiguous governance terms ('verify', 'check', 'validate')
Selects the easiest interpretation -- usually existence check -- not the most appropriate one
Use declared QA levels from CS-GOV-005. Never use unscoped QA terms.

# 2. CS-AI-002 -- Agent Corespine

CS-ID:  CS-AI-002
Tags:  AI | AGENT | AUTHORITY | EXECUTION | COMPOSITION | PERMISSION
Root Goal:  Govern all agent definitions, authority levels, compositions, and executions -- ensuring every agent is a declared, bounded executor with explicit authority and traceable audit trails
Layer
Elements
Rule
Root
Declared, bounded execution
An agent does not know how to do things -- it knows which skills to invoke in which order. Every agent is bounded by its Skill Permission List.
Trunk
Agent Backpack (20 slots)
Identity, authority level, pipeline reference, skill permission list, goal declaration, entry state, context, skill sequence, branch criteria, failure handling, reasoning, wiring state, relationships, audit trail template, escalation history, depth declaration. All 20 slots.
Branch -- Authority Levels
CORE (human-in-the-loop), MEDIUM (confirmed at branches), FULL (autonomous within constraints)
Three levels. Escalation requires Governor approval (GOV-[YEAR]-[SEQUENCE]) and audit trail evidence.
Branch -- Simulation Agent
AG-ORCH-SIM-0001 -- six personas, eleven-step protocol
Specific agent for pre-build structural validation. CORE in Sprint 2, MEDIUM after Governor approval in Sprint 3.
Branch -- Multi-Agent Pipelines
Sequential composition, explicit handoffs, unified audit trail
No parallel agents on shared state. No agent can invoke another at higher authority than itself.
Sub-branch -- Escalation Protocol
Six-step process: execution count minimum, clean audit trail, gap density review, escalation request, Governor review, registry update
No informal escalation. Every authority level requires documented evidence.

# 3. CS-AI-003 -- Skills Corespine

CS-ID:  CS-AI-003
Tags:  AI | SKILL | ATOMIC | CAPABILITY | DOMAIN | REGISTRY | COMPOSABLE
Root Goal:  Govern all skill definitions -- ensuring every skill is atomic at definition, composable at orchestration, and registered before use
Layer
Elements
Rule
Root
Atomic capability
A skill does one thing. One verb phrase. One input contract. One output contract. Skills that do two things are two skills that have not been separated.
Trunk
Skill Backpack (18 slots at MEDIUM)
ID, name, domain, input/output contracts at Core/Medium/Full, failure modes at each depth, reasoning, composition guidance, wiring state, sprint_ready field, audit checkpoint, Dynamic Completion registration.
Branch -- Seven Domains
PIPELINE, CORESPINE, GAP, PAGE, ELEMENT, TEMPLATE, UI, ORCH, AGENT, VOCAB, GPOW (11 declared domain codes)
Every skill belongs to exactly one domain. Cross-domain skills are two skills.
Branch -- Orchestration Skills
SK-ORCH-0001 (ZF), SK-ORCH-0002 (Priority Scoring), SK-ORCH-0003 (GPOW Registry), SK-ORCH-0004 (Gap Density), SK-ORCH-0005 (P5 Resource Check), SK-ORCH-0006 (Pattern Report)
Platform-critical skills. All at Defined status until Sprint 2.
Branch -- Gap Detection Skills
SK-GAP-0001 through SK-GAP-0006 -- one per gap type
Each detects exactly one gap type. Atomic.
Branch -- GPOW Skills
SK-GPOW-0001 (Seed Case Selection)
One declared GPOW skill. More added as GPOW phases are implemented.
Sub-branch -- Composition Rule
Skills never call other skills directly. Agents compose skills. Orchestrators bundle compositions.
Hidden skill-to-skill calls are undeclared agents. Declare them as agents in CS-AI-002.

# 5. CS-OPS-002 -- Automation Corespine

CS-ID:  CS-OPS-002
Tags:  OPS | AUTO | TRIGGER | PIPELINE | AGENT | CONTINUOUS | SCHEDULED
Root Goal:  Govern all automation -- ensuring every automated action is declared, triggered by ratified conditions, executed by ratified agents, and audited
Layer
Elements
Rule
Root
Declared automated behavior
No automation without declaration. An automated action that is not declared is an ungoverned action.
Trunk -- Automation Types
Event-triggered (fires on declared condition), Scheduled (fires at declared interval), Continuous Loop (fires on every platform event), Pipeline-triggered (fires on pipeline stage completion)
Type declared at creation. Trigger condition declared and ratified.
Branch -- Continuous Automations
Dynamic Completion Loop, Learning Loop, ZF-REGISTRY auto-rejection, Priority Engine re-scoring
Continuous automations are Continuous Loops (CS-STRUCT-002, LOOP-CONT). Governed by CS-GOV-001 (can only be terminated by Governor).
Branch -- Event-Triggered Automations
Wiring state change -> re-scoring trigger, Vault entry -> propagation analysis, GPOW phase completion -> Pattern Report
Trigger-action pairs are declared and ratified. No implicit automations.
Branch -- SaaS Automation Inheritance
When platform builds SaaS solutions, automations are exported as ratified automation packages
SaaS solutions inherit automation governance. External users cannot activate unratified automations.
Sub-branch -- Automation Audit Trail
Every automated action logs: trigger event, agent/skill invoked, output, timestamp
No silent automation. Every automation execution is traceable.
