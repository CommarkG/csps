# 1. Root and Trunk -- CS-AI-COM

CS-AI-COM ROOT   Every communication event in this platform is a governed act. The direction of communication determines the template, the DNA that must be present, the depth of context required, and the format of the output. Communication without a declared pattern is communication that cannot be audited, reproduced, or improved.
Trunk Property
Definition
Root Goal
Govern every communication direction in the platform -- ensuring that platform DNA, ratified vocabulary, and declared context travel in every message regardless of who is sending or receiving
Root Principle
Every message carries three things: the platform DNA (corespine reference, ratification state, vocabulary alignment), the operational context (what is being requested, why, at what depth), and the expected output contract (what the receiver must produce)
What All Branches Share
Platform DNA injection in every message. Ratified vocabulary use. Declared output contract. No communication without these three.
Inherited By
Every agent, every skill invocation, every wizard session, every simulation pass, every external AI request, every developer report
Hardwired Enforcement
The platform's context bundle validator checks for DNA presence before any communication executes. A message without platform DNA is rejected -- not flagged. Rejected.

## 1.1 Platform DNA -- What Must Be Present in Every Message

'Platform DNA' is the minimum set of context that every message must carry regardless of communication branch. It is what makes the receiver's behavior governed rather than default.
DNA Element
Content
Why Mandatory
Vocabulary alignment declaration
'In this communication, [term] means [CSPS definition].' Declared for any CSPS native term used.
Without this, receivers import their own definitions. Foreign definitions produce foreign behavior.
Corespine reference
Which corespine(s) govern the subject of this communication. Example: 'This request operates within CS-STRUCT-002 (Loops) and CS-GOV-002 (Priority).'
Corespine reference anchors the communication to the governed lineage. Without it, the receiver cannot know which rules apply.
Ratification state declaration
Status of the elements being communicated about: RATIFIED / DRAFT / PENDING.
Receivers must know whether what they are working with is constitutional or provisional.
Depth declaration
Which depth level (CORE / MEDIUM / FULL) is being requested or provided.
Without depth declaration, receivers default to their own depth preference -- which may be wrong for the context.
Output contract
What the receiver must produce: format, fields, depth, delivery mechanism.
Without an output contract, the receiver defines success themselves. That is not governed communication.

# 2. COM-1 -- Human -> Human

COM-1   How humans communicate with each other within the platform context -- ensuring shared vocabulary, ratified terminology, and decision recording even in informal human-to-human exchanges.
Branch ID:  COM-1
Direction:  Human -> Human
Core Purpose:  Prevent vocabulary drift and undeclared decisions in human-to-human communication about platform matters
COM-1 Rule
Definition
Use ratified vocabulary
When discussing platform matters, use only terms from the CS-GOV-003 Vocabulary Registry. If a term is not in the registry -- flag it as unregistered before using it.
Declare decision status
When a human-to-human discussion produces a decision about the platform -- declare it explicitly: 'This is a decision: [what was decided].' Undeclared decisions are not decisions -- they are conversation.
Record significant decisions
Any decision that affects a ratified element, a corespine, a protocol, or a pipeline must be recorded as a Governor Decision (GOV-[YEAR]-[SEQUENCE]) or a session note with explicit follow-up action.
No informal vocabulary changes
If a human-to-human conversation produces a better term for something -- it is a vocabulary change proposal, not a vocabulary change. It must go through CS-GOV-003 Tier 2 approval before use.
Platform context declaration
When a human-to-human discussion is about the platform -- declare it: 'We are discussing [scope] within [corespine context].' This keeps the conversation anchored.

Branch ID:  COM-2

Core Purpose:  Ensure every human instruction to AI carries the platform DNA that governs AI behavior -- preventing AI from defaulting to training patterns instead of platform patterns

# 4. COM-3 -- Native AI -> Human

COM-3   How AI communicates back to humans -- report formats, finding declarations, permission requests, uncertainty declarations. Includes a Platform Governor sub-branch for constitutional communications.
Branch ID:  COM-3
Direction:  Native AI -> Human (Developer and Governor)
Core Purpose:  Ensure AI outputs are structured, honest about certainty levels, and formatted for human decision-making -- not for AI convenience
COM-3 Core -- Standard AI to Developer Communication
Output Type
Required Structure
Certainty Labeling
Finding report
WHAT: specific element and gap type. WHY: root cause one sentence. IMPACT: P1 score. RECOMMENDATION: specific action not generic guidance.
[KNOW] = confirmed from ratified source. [INFER] = derived from context. [ASSUME] = not confirmed -- declare assumption explicitly.
Permission request
WHAT I want to do: specific action. WHY: justification. SCOPE: what it affects. RISK: blast radius assessment. ALTERNATIVES: what else I considered.
Never proceed without permission on: vocabulary changes, corespine modifications, ratification recommendations, scope expansions.
Progress declaration
WHAT was completed: specific deliverables. WHAT changed: explicit delta from previous state. WHAT is next: specific next action with dependencies.
Never declare done without GPOW evidence. Declare proximity to done as 'functional proof achieved -- generalization and scale proof pending.'
Uncertainty declaration
When uncertain: declare it explicitly before proceeding. 'I am uncertain about [specific thing]. My assumption is [assumption]. Proceeding on this assumption -- please correct if wrong.'
Never blend certainty levels in a single statement. Each claim carries its own label.
Escalation request
WHAT requires Governor: specific decision. CONTEXT: what led here. OPTIONS: what choices exist. RECOMMENDATION: what I recommend and why.
Escalations carry [INFER] or [ASSUME] labels on recommendations. Only facts are [KNOW].

# 8. COM-7 -- Native AI -> Internal Personas

COM-7   How AI instantiates and communicates with internal simulation personas -- persona briefing format, lens declaration, finding format contract, pattern observation requirement. Personas are not free-form reviewers. They are governed sub-agents with declared specializations.
Branch ID:  COM-7
Direction:  Native AI -> Internal Personas
Core Purpose:  Ensure simulation personas receive complete briefings that activate their declared lens -- and that their findings are produced in a format that enters the GPOW Insight Registry without reformatting
COM-7 Persona Briefing Template
Briefing Element
Content
Why Required
Persona identity
Which of the six declared personas is being instantiated. Exactly as declared in 0060 Section 3.
Prevents persona drift -- the persona must behave as declared, not as the AI's interpretation of the persona.
Lens focus declaration
The specific gap types this persona is optimized to detect. Copied from 0060 Section 3 Primary Gap Types column.
Activates the correct detection bias. Without this, the persona defaults to general review.
Scope declaration
Exactly what is being reviewed: document IDs, element IDs, or component names.
Without scope, the persona cannot determine where to focus. Unfocused personas produce unfocused findings.
Vocabulary context
CSPS native terms relevant to the scope. Declared meanings.
Prevents persona from importing training vocabulary for CSPS native terms.
Finding format contract
Exact format required: {ins_id, gap_type: 1-6, element_id, description, root_cause, p1_score, p4_score, backward_targets: [], patterns_observed: []}
Without format contract, findings require reformatting before entering the registry. Reformatting introduces error.
Pattern observation requirement
After individual findings, the persona must declare cross-finding patterns: which gap types appeared more than once, which elements appeared in multiple findings.
Pattern observations are Learning Loop inputs. Without this requirement, the pattern extraction step is skipped.
Depth instruction
Which depth level to review at: CORE (existence and position), MEDIUM (wiring state and relationships), FULL (structural coherence and inheritance chains).
Without depth instruction, personas default to their own preferred depth -- which may be wrong for the session type.
Boundary declaration
What the persona is NOT reviewing. Explicit exclusion prevents overlap between personas.
Without exclusion boundaries, personas duplicate each other's findings -- inflating gap density.
