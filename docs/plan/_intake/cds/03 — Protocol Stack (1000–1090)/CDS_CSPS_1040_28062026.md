What it receives:  A validated, gap-free pipeline with a complete corespine map. Stages are fully defined with backpacks. No page assignments exist yet.

Page Distribution is the moment the abstract becomes navigable. The pipeline exists as logic. This protocol gives that logic a location -- spreading stages across pages in an order that serves the user's cognitive journey, not the developer's convenience.
ZERO FINDINGS MANDATORY   Before any page assignment -- check what page templates already exist in the system. A page type that already exists must be used before a new one is created. Page creation without checking for existing templates is the page-level equivalent of an Orphan Stage.

# 2. What Page Distribution Is -- and Is Not

Page Distribution is the assignment of pipeline stages to pages based on logical grouping, cognitive load, corespine membership, and inherited context flow. It is not a visual layout exercise. It is not a wireframing session. Pages do not exist yet as visual objects -- they exist as logical containers.
A page is a container of pipeline moments -- not a visual concept. Its boundaries are determined by logic, not by aesthetics. UI expression comes later. Pages come first.
The most common failure at this stage: assigning stages to pages based on how they look together, not on what they logically belong together. Visual grouping and logical grouping are not the same thing. When they conflict, logical grouping wins -- always.

# 4. The Distribution Decision Framework

Every stage assignment decision must pass four questions before it is final. These questions are not guidelines -- they are gates within the distribution process.

## 4.1 The Four Distribution Questions -- In Order

Q1 -- What is the logical grouping?
Which stages belong together because they serve the same micro-goal or share the same corespine segment? Logical grouping is the primary criterion. Stages that serve different micro-goals must be separated -- even if they look similar visually.
Q2 -- What is the cognitive load of this grouping?
How many decisions, inputs, or actions is the user being asked to make on this page? A page that asks for more than one primary action is overloaded by definition. Cognitive load determines whether a logical grouping should be split across pages or can coexist on one.
One page -- one primary action. Secondary context may support it. But the user must never face two equally weighted demands on the same page.
Q3 -- Does this grouping create an inheritance break?
When stages are assigned to pages, stages that were adjacent in the pipeline may end up separated across pages. Every such separation must be checked: does the receiving page have full access to the accumulated inheritance from all previous stages -- or has a page boundary created a break?
ZERO FINDINGS MANDATORY   Before finalizing any page assignment -- check whether the stages being separated have inheritance relationships. A stage that inherits from a stage on the previous page requires an explicit page-to-page handoff declaration. Check inheritance before separating.
Q4 -- What is the optimal sequence on this page?
Once stages are assigned to a page, their internal order must be determined. Order is not neutral. It follows: what the user needs to understand first, what builds trust before asking for commitment, what is the natural next question in the conversation this page is having.

# 5. Page Type Registry

Pages are not invented fresh for every pipeline. They belong to declared types. A page type is a validated pattern that defines the structural role a page plays in the pipeline. Using a declared page type gives the page an inherited identity -- its corespine position, its cognitive load profile, and its expected stage types are already partially defined.
ZERO FINDINGS MANDATORY   Before assigning a stage to a page -- check the Page Type Registry. If a matching type exists, use it. If no matching type exists, create a new type -- but creating a new type requires explicit justification that no existing type covers this page's role.

# 7. Responsive Distribution

Every page assignment decision has a responsive dimension. The same pipeline stages assigned to a page may need different ordering, different grouping, or different split decisions when the viewport changes from desktop to mobile.
Responsive design is not stacking desktop layouts vertically. It is re-sequencing the pipeline logic for a different reading and interaction pattern. On mobile, vertical order IS hierarchy. What appears first gets attention. The pipeline stage that is primary must appear first -- always.
