# 1. Position in the System

When this runs:  After Element Definition Protocol (1050) is complete. Before UI Expression Protocol (1070).
What it receives:  Validated elements with complete backpacks, registered in the Element Registry, assigned to pages with declared context weights.
What it produces:  Self-aware page template objects -- each carrying its own complete context, pipeline position, element registry, recurring element definitions, and forward obligations. Templates that AI can duplicate without reconstruction.
This is the document that closes the reconstruction loop. Every time an AI engine touches a page, it currently reconstructs context from scratch -- re-reading documentation, re-inferring relationships, re-guessing what belongs where. This protocol ends that. A page template is a self-aware context object. When it is duplicated, everything it knows about itself is duplicated with it.
A page template is not a visual layout. It is a governed context object that knows its pipeline position, its corespine membership, its inherited elements, and its obligations forward -- and carries all of this intrinsically, without requiring external retrieval.
ZERO FINDINGS MANDATORY   Before creating any page template -- check the Template Registry. A template for this page type may already exist. A template already built to Core depth needs Medium added -- not a new template created. One-time effort, infinite reuse is the governing principle.

# 2. What a Page Template Is

A page template is a self-contained, self-aware context object that represents a validated page type. It carries everything an AI builder, orchestrator, or developer needs to instantiate a correct, governed page -- without consulting any external document, without reconstructing context, and without guessing.

The most expensive failure this standard prevents: an AI engine that receives a page template and immediately begins reconstructing what it means, what goes on it, and what the elements should do -- because the template contained no intrinsic context. That reconstruction is where intent evaporates and defaults take over.

## Layer 3 -- Recurring Element Registry

# 4. The Template Registry

Every template defined using this standard is registered in the Template Registry. The registry enables Zero Findings checks, tracks instantiation counts, and is the propagation target for Dynamic Completion when a template is improved.
ZERO FINDINGS MANDATORY   The Template Registry is the first check before any page is created. If a template exists for the required page type, that template is used. If it does not exist, a new template is created -- and immediately registered. A page created without a template is an ungoverned page. Ungoverned pages are not permitted.

# 5. Instantiation Protocol

Instantiating a template means creating a new page from it. Instantiation is not copying -- it is inheritance. The new page inherits the template's full context object and adds only what is specific to its pipeline assignment and content.
Instantiation Step
Action
Rule
1 -- Zero Findings
Check the Template Registry for the required page type. Confirm the template exists and its build depth is sufficient.
If template is at Core but Medium is needed -- build Medium first. Do not instantiate at a depth the template has not reached.
2 -- Pipeline Assignment
Assign the specific pipeline stages this instantiation will serve. Populate the Pipeline Position slot with the specific stage IDs.
The assigned stages must be validated in the Page Map from 1040. No ad-hoc stage assignment on instantiation.
3 -- Inheritance Population
Populate the Entry State and Accumulated Inheritance slots with the specific context arriving from the preceding page in this pipeline.
Must match the Forward Obligation declaration of the preceding page exactly.
4 -- Recurring Element Configuration
For each recurring element -- confirm variant and context weight for this specific instantiation.
Variant is determined by pipeline stage and page type. The template's recurring element registry provides the range. The orchestrator selects within that range.
5 -- Customization Boundaries
Apply any pipeline-specific content within the declared customization boundaries.
Nothing outside the customization boundaries may be changed. Template governance is not optional.
6 -- Forward Obligation Declaration
Populate the Forward Obligation slots with the specific context this instantiation will pass to the next page.
Must align with the Relationship Forward declaration in the template.
7 -- Wiring State Declaration
Declare the wiring state of this instantiation.
An instantiation is only Current if the template is Current, the preceding page's forward obligation is Current, and all populated slots are Current.
DYNAMIC COMPLETION   Every template improvement -- a new recurring element, an improved sub-context definition, a refined instantiation rule -- is a vault entry. The improvement propagates to all existing instantiations of that template. This is the mechanism that makes template investment compound over time.
