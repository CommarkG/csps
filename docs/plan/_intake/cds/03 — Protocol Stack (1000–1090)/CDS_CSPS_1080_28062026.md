# 1. What the Loop Orchestrator Is

Origin:  The Loop Orchestrator closes the conversation that started this entire suite. The original insight: what was called 'Zero Findings iterations' are actually loops -- structured iterations toward a goal. This protocol formalizes that insight as a governed mechanism.
Definition:  The Loop Orchestrator is the mechanism that coordinates multiple loops -- each a governed iteration cycle -- toward a declared overarching goal. It manages loop dependencies, loop state, loop priority, and loop completion signals. It is the corespine loop engine.
Relationship to pipelines:  A pipeline defines the stages from need to resolution. A loop is a pipeline that may iterate -- where the resolution of one cycle becomes the entry state of the next. The Loop Orchestrator governs when iteration continues, when it stops, and what the next cycle should prioritize.
LOOP PRINCIPLE   A loop is not a failed pipeline. It is a pipeline that recognizes that complex goals are not achieved in one pass. Each iteration brings the platform closer to the goal -- carrying accumulated state forward, incorporating learnings, and letting the Priority Engine determine what the next iteration should tackle.
ZERO FINDINGS MANDATORY   Every loop iteration begins with Zero Findings. Before any action in any cycle -- check what the previous cycle produced, what is already resolved, and what remains. A loop that does not begin with Zero Findings will redo work, miss progress, and lose accumulated state.

# 2. Loop Anatomy -- The Five Elements

Every loop managed by the Loop Orchestrator has five declared elements. A loop without all five is not a governed loop -- it is an uncontrolled iteration.
Loop Element
Definition
What Happens Without It
Overarching Goal
The single outcome the loop is working toward -- declared once and inherited by every cycle. Traceable to Pipeline Protocol Q5.
Without a declared goal, iterations have no convergence signal. The loop runs indefinitely with no way to declare completion.
Cycle Entry State
The accumulated state at the start of each cycle -- what has been achieved so far, what was learned in the previous cycle, what remains. Carried forward from the previous cycle's exit state.
Without declared entry state, each cycle starts from scratch. The loop loses accumulated progress and redoes completed work.
Cycle Goal
The specific micro-outcome this cycle will achieve. A contribution toward the overarching goal, sized to available resources.
Without a cycle goal, the iteration has no completion signal. It ends when resources run out -- not when the goal is achieved.
Priority-Governed Action Sequence
The ordered set of actions for this cycle -- selected by the Priority Engine from the remaining goal backlog, scoped to available resources, assembled as an Optimal Bundle.
Without priority governance, cycles execute arbitrary actions. The most valuable work may never get done because lower-priority work consumed the resources.
Cycle Exit State
What was achieved, what changed, what was learned, what remains. Passed forward as the next cycle's entry state. Forwarded to Dynamic Completion vault.
Without declared exit state, the loop loses its accumulated context between cycles. The next cycle cannot inherit from this one.

# 3. Loop Types -- Three Patterns

The Loop Orchestrator governs three distinct loop patterns. Each pattern has a different convergence model -- a different definition of what done looks like.

## 3.1 Convergence Loop

LOOP PRINCIPLE   A loop that iterates toward a fixed, declared goal. Each cycle reduces the distance between current state and goal state. The loop terminates when the goal state is achieved and the resolution signal is produced.
Property
Value
Convergence signal
The overarching goal's resolution signal -- same as Pipeline Protocol Q5
Cycle relationship
Sequential -- each cycle builds on the previous. No cycle is independent.
Termination condition
Resolution signal produced. Or: Platform Governor declares convergence impossible and terminates with reason.
Priority Engine role
Scores remaining goal backlog against six parameters each cycle. Highest-priority remaining actions form the next cycle's bundle.
Example
Building a complete pipeline definition. Each cycle adds stages, resolves gaps, adds corespine declarations. The loop terminates when Gap Detection passes all three passes clean.

## 3.2 Refinement Loop

LOOP PRINCIPLE   A loop that iterates to improve something that already exists to an adequate state. The goal is not a binary achieved/not achieved -- it is a quality threshold. The loop terminates when the output meets the declared quality threshold.
Property
Value
Convergence signal
Quality threshold -- a declared measurable standard that the output must meet
Cycle relationship
Each cycle refines the same output -- not extending it but improving it
Termination condition
Quality threshold met. Or: Platform Governor declares threshold unachievable with current resources and accepts current quality with declaration.
Priority Engine role
P4 (Readiness) and P3 (Gap Resolution) dominate -- simplest improvements first, restoration before creation
Example
Improving element backpack definitions to Medium depth. Each cycle addresses the lowest-quality backpack slots. Loop terminates when all slots meet Medium depth quality criteria.

## 3.3 Exploration Loop

LOOP PRINCIPLE   A loop that iterates to discover -- not to converge on a fixed goal but to map an unknown space. Each cycle reveals new information that updates the goal definition. The loop terminates when the discovery is sufficient for a Convergence or Refinement Loop to begin.
Property
Value
Convergence signal
Discovery sufficiency -- declared by Platform Governor when enough is known to define a fixed goal
Cycle relationship
Each cycle expands the known space. Previous cycle findings update the next cycle's direction.
Termination condition
Platform Governor declares discovery sufficient. Or: Maximum exploration cycles reached without sufficient discovery -- escalated for goal redefinition.
Priority Engine role
P2 (Enablement Factor) dominates -- actions that reveal the most new information execute first
Example
The Goal Definition Wizard (2000) runs an Exploration Loop when the human's initial goal statement is too vague for a Convergence Loop. Each cycle asks probing questions that narrow the goal until it is lockable.

# 4. The Loop Orchestrator Mechanism

The Loop Orchestrator runs between cycles -- not within them. Within a cycle, the Core Engine (3000) governs execution. The Loop Orchestrator governs the transitions between cycles: what was achieved, what comes next, and whether the loop should continue or terminate.

# 5. Multi-Loop Architecture -- When Goals Require More Than One Loop

Complex goals may require multiple loops running in dependency order. The Loop Orchestrator manages loop dependencies -- ensuring that a loop that depends on another loop's output does not begin until its dependency loop has achieved its resolution signal.
Multi-Loop Rule
Definition
Dependency declaration
Every loop declares its dependencies at definition time. A loop that depends on Loop A's output cannot begin until Loop A produces its resolution signal.
No parallel loops on shared state
Two loops that modify the same platform state cannot run simultaneously. The Loop Orchestrator serializes them -- highest Priority Engine score runs first.
Loop hierarchy
The overarching goal sits above all loops. Loops serve the overarching goal -- they do not define it. If a loop's output diverges from the overarching goal, the loop is reassessed before continuing.
Nested loops
A loop may contain sub-loops -- a Convergence Loop whose cycle goal is itself achieved through a Refinement Loop. The outer loop's cycle goal is the inner loop's overarching goal.
Loop handoff state
When Loop A produces its resolution signal and Loop B begins -- Loop A's exit state becomes Loop B's initial entry state. The accumulated context chain transfers completely.
The Loop Orchestrator is the corespine of the platform's evolution. Just as a corespine gives every element a lineage, the Loop Orchestrator gives every iteration a lineage -- where it came from, what it achieved, and what it owes the next cycle.

# 7. Integration With Priority Engine and Bundling

The Loop Orchestrator, the Priority Engine (0040), and the Bundling Philosophy (0050) form the execution triad of the platform. Each governs a different dimension of the same question: what gets done, in what order, and how is it packaged?
Component
Governs
How They Interact
Loop Orchestrator (1080)
WHAT the platform is working toward -- the goal structure and iteration cadence
Provides the overarching goal and remaining backlog to the Priority Engine. Receives priority-ordered action list back.
Priority Engine (0040)
WHICH actions execute FIRST within and across loops
Receives remaining backlog from Loop Orchestrator. Scores against six parameters. Returns priority-ordered list to Bundling Engine.
Bundling Philosophy (0050)
HOW actions are packaged for execution -- optimal bundles within resource constraints
Receives priority-ordered list from Priority Engine. Assembles Optimal Bundle. Returns Bundle Manifest to Loop Orchestrator for cycle execution.
LOOP PRINCIPLE   Goal without priority is aspiration. Priority without bundling is a ranked list. Bundling without loops is a one-shot execution. The three together are the platform's execution intelligence -- iterating toward goals, choosing what matters most, and packaging execution for maximum efficiency within real constraints.
