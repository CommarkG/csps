# 1. The Problem With Done

Done is the most abused word in software development. It is declared when effort is sufficient -- when someone decides enough work was done. It is declared when a checklist is exhausted -- when every step was completed. It is declared when tests pass -- when the specific cases that were tested produced green results.
None of these are done. They are proximity to done. They are done-adjacent. They share one fatal flaw: they prove process, not working. They prove that something was attempted -- not that it works.
Done is not a declaration. Done is a proof. And proof requires evidence from real conditions across growing diversity -- not from the controlled conditions of the build environment where everything was designed to work.
GPOW PRINCIPLE   Done is declared only when a mechanism is proven to work continuously across a growing, intentionally diverse set of real conditions -- verified to real Zero Findings at each step -- with the mechanism itself improved at each expansion before the next expansion begins.
This is not caution. This is the fastest path to stable scale. Every organization that declares done without proof and goes directly to full scale spends ten times as long fixing at scale what would have been trivial to fix at small scale. The gradual path is the fast path.

# 2. The Backward Propagation Imperative

This is the principle most consistently violated in iterative development -- and most completely ignored by AI agents.
BACKWARD PROPAGATION IMPERATIVE   When an insight is found at any GPOW phase, it travels in two directions simultaneously. Forward: all future cases are built with this improvement embedded. Backward: all previously completed cases are revisited and improved. Both directions are mandatory. Neither is optional.
Why AI agents violate this by default: an AI agent processes sequentially. It builds element 1, then element 5, then element 12. When it finds an insight at element 12, its context window contains elements 8-12. Elements 1-7 are not in context. They are not revisited. The insight is applied forward and the previous work silently diverges from the current standard.
This is not a failure of intent. It is a structural failure -- the insight has no mechanism that forces it backward. Without such a mechanism, every AI-assisted build accumulates an invisible layer of inconsistency between early work and late work. The platform looks coherent on the surface. It is structurally fractured underneath.
An insight found at batch 3 that is not applied to batches 1 and 2 produces a platform where the first elements built are always the least current. The longer the build, the more the early work diverges from the evolved standard. This is the most common source of platform inconsistency -- and the most invisible.
BACKWARD PROPAGATION IMPERATIVE   The Backward Propagation Imperative is hardwired into every GPOW phase transition. Before expanding to the next phase, every insight from the current phase is propagated backward to all previously completed elements. This is not optional. It is the gate that must be passed before expansion proceeds.

# 3. GPOW as a Loop -- The Refinement Loop Structure

GPOW is a Refinement Loop (defined in Loop Orchestrator Protocol 1080) with adaptive cycle sizing governed by gap density. The overarching goal is proof of working at full scope. Each phase is a cycle. The expansion rate is governed by what the previous cycle revealed.
Loop Property
GPOW Value
Loop Type
Refinement Loop -- iterating to meet a quality threshold (proof of working at full scope)
Overarching Goal
Mechanism proven to work continuously across full scope with real Zero Findings
Cycle = Phase
Each GPOW phase is a Loop Orchestrator cycle -- with its own entry state, cycle goal, and exit state
Adaptive expansion rate
Gap density from each phase determines next phase expansion size -- high gap density = smaller expansion, low gap density = larger expansion
Termination condition
Full scope covered with Zero Findings across two doublings of the final phase set
Backward propagation
Mandatory at every phase transition -- before expansion, all insights travel backward

# 4. The Four GPOW Phases


## Phase 1 -- Seed

GPOW PRINCIPLE   One case. The most representative, most central case. Not the easiest case. Not the most convenient case. The case that best represents the core purpose of the mechanism being tested.
Phase 1 Element
Definition
Case selection criterion
The single most representative case -- the one that would expose the most fundamental failures if the mechanism is wrong
Completion standard
Real Zero Findings -- not declared done, not checklist complete. Actually working with no gaps, no misalignments, no failures. ZF must be re-run after every fix, not just once.
What is documented
Every finding -- gap, misalignment, insight -- with full description, root cause, and the improvement made to the mechanism as a result
Backward propagation
At Phase 1 there is nothing to propagate backward to. But every insight is registered in the GPOW Insight Registry for forward propagation to all future phases.
Gate to Phase 2
Real Zero Findings achieved on the seed case. Mechanism improved based on all Phase 1 findings. GPOW Insight Registry populated. No gate passage without documented mechanism improvement.

## Phase 2 -- Variance

GPOW PRINCIPLE   Add the most different cases -- maximum variance from the seed and from each other. Small number: 2 to 3 cases. Same standard: real Zero Findings for each. This phase proves the mechanism generalizes -- not just that it works for the seed case.
Phase 2 Element
Definition
Case selection criterion
Maximum variance from Phase 1 seed AND from each other. If Phase 1 was a simple linear case, Phase 2 should include a branching case and an edge case. Variance is structural -- different pipeline type, different corespine family, different page type, different element complexity.
Completion standard
Real Zero Findings for each case in this phase. Cases are not batched -- each is proven individually before the next begins.
What is documented
Every finding per case, plus cross-case pattern analysis: are the same gaps appearing across different cases? A pattern is a systemic issue, not a case-specific one.
Backward propagation
Every insight from Phase 2 propagates backward to Phase 1 seed. The seed is revisited and improved. If Phase 2 reveals that the seed was actually incomplete -- the seed is re-proven to Zero Findings before Phase 3 begins.
Adaptive expansion
Gap density check: if Phase 2 produces more than 3 gaps per case -- Phase 3 expansion is conservative (2-3 cases). If Phase 2 produces 0-1 gaps per case -- Phase 3 expansion can be aggressive (5-8 cases).
Gate to Phase 3
Real Zero Findings on all Phase 2 cases. Mechanism improved based on all Phase 2 findings. Phase 1 seed re-proven if Phase 2 insights changed it. Gap density assessed for Phase 3 sizing.

## Phase 3 -- Scale Confirmation

GPOW PRINCIPLE   Double (or more, if gap density was low in Phase 2). Choose cases maximally different from all previous cases AND from each other. At each doubling, improve the mechanism before expanding further. This phase proves the mechanism holds at emerging scale.
Phase 3 Element
Definition
Case selection criterion
Maximally different from all Phase 1 and Phase 2 cases. Actively seek the cases most likely to break the mechanism -- not the cases most likely to pass.
Expansion rate formula
Base expansion: 2x Phase 2 count. Modified by gap density: if Phase 2 gap density > 3 per case, use 1.5x instead of 2x. If Phase 2 gap density = 0, use 3x.
Completion standard
Real Zero Findings for each case. Cross-case pattern analysis mandatory after each sub-batch of 3-4 cases.
What is documented
All findings plus: mechanism improvement log -- what changed in the mechanism as a result of Phase 3, and what the improvement enables going forward.
Backward propagation
Every insight from Phase 3 propagates backward to ALL Phase 1 and Phase 2 cases. This is the most important backward propagation in GPOW. Phase 3 insights are typically the most significant because they emerge from higher diversity.
Mechanism improvement gate
After every sub-batch within Phase 3 -- the mechanism is improved before the next sub-batch begins. Expansion without improvement is not permitted within Phase 3.
Gate to Phase 4
Real Zero Findings across all Phase 3 cases. Mechanism improved at each sub-batch gate. All Phase 1 and Phase 2 cases re-verified against Phase 3 mechanism improvements. Gap density assessed for Phase 4 sizing.

## Phase 4 -- Full Scope

GPOW PRINCIPLE   Double the Phase 3 count -- twice. Each doubling is its own sub-phase with Zero Findings verification and backward propagation before the next doubling. After two doublings, go to full scope. Done is declared only here -- never before.
Phase 4 Element
Definition
Sub-phase 4a
Double Phase 3 count. Maximum variance selection. Real Zero Findings. Mechanism improvement. Backward propagation to all previous phases.
Sub-phase 4b
Double sub-phase 4a count. Same standard. Same backward propagation obligation.
Full scope
All remaining cases. At this point, the mechanism has been proven across four graduated phases with continuous improvement. Full scope should produce near-zero new gaps.
Expected gap rate at full scope
If GPOW phases were executed correctly, full scope should produce 0-5% of the gap rate seen in Phase 1. A higher gap rate signals that a phase was completed without real Zero Findings or without genuine mechanism improvement.
Backward propagation at full scope
Any gaps found at full scope propagate backward through the entire completed set -- all previous phases. No gap found at full scope is a local fix. It is a systemic improvement.
Done declaration
Done is declared when: (a) full scope is covered, (b) Zero Findings confirmed across the full set, (c) all backward propagations from full scope are complete, (d) Platform Governor signs the GPOW closure declaration.

# 5. The GPOW Insight Registry

With a registry, backward propagation is a tracked obligation with declared recipients and confirmed completion.

# 6. Adaptive Expansion -- Gap Density Governs Pace

The expansion rate between phases is not fixed. It is governed by the gap density of the completed phase -- the number of gaps found per case. High gap density signals the mechanism is not yet stable enough for aggressive expansion. Low gap density signals the mechanism is ready for more.
Gap Density
Definition
Next Phase Expansion Rate
Signal
Critical -- > 5 gaps per case
The mechanism has fundamental issues not yet resolved
Do not expand. Re-run current phase with improved mechanism.
The mechanism is not proven at current scale. Expansion would spread unresolved issues.
High -- 3-5 gaps per case
The mechanism works but has significant gaps
Expand conservatively -- 1.5x current case count
Expansion is permitted but must be cautious. Each new case is expected to reveal more gaps.
Standard -- 1-3 gaps per case
The mechanism is working with minor issues
Expand at standard rate -- 2x current case count
Normal GPOW progression. Gaps are decreasing. Mechanism is improving.
Low -- 0-1 gap per case
The mechanism is proven at current scale
Expand aggressively -- 3x current case count
The mechanism is stable. Expansion can be faster. Remaining gaps are likely edge cases.
Zero -- 0 gaps across all cases in phase
The mechanism is proven stable at current scale
Expand maximally -- 4x or move directly to next phase
Exceptional signal. Mechanism has zero known failures at this scale.
GPOW PRINCIPLE   Gap density is re-calculated after every sub-batch within a phase -- not just at phase completion. A phase that starts at Low gap density but produces a High gap density sub-batch mid-phase must slow expansion before continuing. Gap density is a real-time signal, not a phase-end summary.

# 7. What GPOW Proves -- Three Levels of Proof

Proof Level
What Is Proved
When Achieved
Functional proof
The mechanism produces correct outputs for a representative case
Phase 1 completion with real Zero Findings
Generalization proof
The mechanism works across diverse cases -- not just the case it was designed for
Phase 2 and Phase 3 completion with backward propagation
Scale proof
The mechanism works at full scope with stability and consistency -- not just at small scale
Phase 4 and Full Scope completion with done declaration
Only Scale Proof qualifies as Done. Functional proof means it works. Generalization proof means it generalizes. Scale proof means it is proven -- and done can be declared. The three are not interchangeable.

# 9. GPOW Applied to the Suite Itself

The CSPS UX/UI Protocol Suite is itself subject to GPOW. The suite has been built -- but it has not been proven. The four-persona review identified 14 gaps. Those 14 gaps are the output of Phase 1 of GPOW applied to the suite itself.
GPOW Phase
Suite Application
Phase 1 -- Seed
Apply the suite to one complete pipeline build from goal definition to UI expression. The four-persona review was a proxy for Phase 1. Real Phase 1 is an actual governed build session using all suite documents.
Phase 2 -- Variance
Apply the suite to 2-3 maximally different pipeline types -- a simple linear pipeline, a multi-corespine pipeline, and a multi-agent pipeline.
Phase 3 -- Scale
Apply the suite to a set of 5-8 pipelines covering all declared page types, all declared element types, and all declared loop types.

BACKWARD PROPAGATION IMPERATIVE   Every insight from every phase of GPOW applied to the suite propagates backward to all previously delivered suite documents. If Phase 2 of suite GPOW reveals that the vocabulary standard (1000) is missing a term needed by agents -- that term is added to 1000, and 1000 is re-proven. The document suite is a living system -- GPOW is the mechanism that keeps it honest.
