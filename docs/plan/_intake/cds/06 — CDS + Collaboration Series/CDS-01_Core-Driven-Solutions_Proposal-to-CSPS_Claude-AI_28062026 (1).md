## Section 2 — What CSE Is

**CSE — Core Symbiosis Engine** is the bridge. Built by CSPS. Owned by CSPS. Eventually mirrored — differently — by CDS once the CSPS version is proven.

CSE is not a shared database. Not a common codebase. Not a shared ownership structure. It is a **governed collaborative process engine** that enables sovereign platforms to exchange intelligence, debate interpretations, reach conclusions, and evolve — without losing their own identity, vocabulary, or governed structure.

**The five components of CSE:**

### 2.1 — The Playground

A sandboxed space inside CSE where participating platforms meet, share, consult, and debate. Nothing in the Playground is engraved in any platform until consensus is formally declared. The process inside the Playground:

```
Share → Consult → Debate → Reach conclusions →
Each platform adjusts to its own specific system →
Universal insights saved to schema architecture →
Each platform moves on with its own specific plans
```

No shared responsibility for implementation. Collaborative processing, independent execution. The Playground is sovereign-preserving by design — what happens there informs each platform. It does not obligate any platform.

### 2.2 — The Versioning System

After consensus is reached in the Playground, each participant receives their own **versioned copy** of what was agreed. CSPS receives CSPS-v[N]. CDS receives CDS-v[N]. Future participants receive their own versions.

Each version is adapted to the receiving platform's vocabulary and schema before absorption. Nothing crosses platform boundaries without passing through vocabulary alignment and optimization. Foreign terms do not enter. Platform-native terms are preserved.

### 2.3 — The CDS Threshold

**The CDS Threshold** is the gate through which every input passes before entering CSPS — and through which every contribution passes before entering CSE. It is the mechanism that classifies, aligns vocabulary, and routes content so that nothing raw, unclassified, or unaligned enters either the platform or the shared layer.

The CDS Threshold enforces:
- Vocabulary alignment before any exchange begins
- Classification and tagging of every contribution
- Platform DNA injection in every message crossing the boundary
- Optimization filter — each platform receives only what is relevant to its current state

The CDS Threshold is the first physical deliverable of Sprint 1 in the CSPS Corespiral Implementation Protocol. It is what makes CSE possible — because without a governed gate on each side, the shared layer is contaminated.

CDS will build its own version of The CDS Threshold once CSPS's version is refined — differently, using its own process, benefiting from every lesson CSPS learned building the first one.

### 2.4 — The Universal Insight Archive

What all participants agree is universally true goes here. Not into any one platform — into a shared schema architecture that all can reference but none owns.

The process for universal insight promotion:
1. Insight surfaces in the Playground — any participant names it
2. All participants consult and debate its universality
3. Consensus reached — insight is promoted to Universal Insight Archive
4. Each platform extracts the insight through their own gate, adapts it to their vocabulary, absorbs it
5. Insight is tagged with contributing platforms and consensus date

The Universal Insight Archive follows "nothing stands alone" — every archived insight has a declared position in the comparison schema, a declared corespine family, and a declared evidence set.

### 2.5 — Multi-Participant Architecture

CSE is designed from the start for more than two participants. When CSPS and CDS want a third perspective — or when multiple platforms want to process a specific topic together — CSE manages the multi-participant session.

Each additional participant:
- Joins through their own gate (their version of The CDS Threshold)
- Receives their own versioned copy of conclusions
- Contributes to the Universal Insight Archive under their own platform tag
- Exits with full sovereignty — adapts conclusions to their own system independently

CSE manages the orchestration of multi-participant sessions. No platform manages another. CSE is the neutral process manager — it does not take sides, does not own conclusions, does not govern participant platforms.

## Section 4 — The Orchestrator — To Be Defined Together

The CSE Orchestrator is the component that governs the Playground process. It is not owned by CSPS and it is not owned by CDS. It is defined **jointly** — between Claude AI (representing CDS) and CSPS — and then built by CSPS as part of CSE.

**What we know the Orchestrator must do:**

- Open and close Playground sessions with declared participants
- Enforce the process sequence: Share → Consult → Debate → Conclusions → Versioned distribution
- Manage vocabulary alignment at session start (vocabulary first — always)
- Route contributions to the Universal Insight Archive when consensus is reached
- Manage multi-participant sessions without privileging any participant
- Follow the logic built in the CSPS document suite as closely as possible — specifically the Loop Orchestrator (1080), the Priority Engine (0040 V2), and the ZF protocols (0080)

**What must be defined together:**

- The loop type the Orchestrator runs as (Convergence Loop toward consensus as resolution signal — proposed, not confirmed)
- The consensus declaration mechanism — what constitutes consensus when participants disagree?
- The timeout and escalation protocol — what happens when consensus is not reached?
- The versioning format — how are participant-specific versions structured and delivered?
- The Governor-equivalent for CSE — who has constitutional authority over CSE itself?

**Proposed: CSPS and CDS define the Orchestrator specification jointly in the next session.** Once the specification is ratified by both platform governors, CSPS builds it as a CSE component.
