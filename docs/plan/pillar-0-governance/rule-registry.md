# The Rule Registry

> **Check what exists. Enhance the ratified thing. Create new only with a justification.**

## What this document locks

The mechanism that turns discussed-and-approved decisions into mechanically enforced rules. Specifically: the rule entry schema, the chat→law workflow, the bidirectional audit invariants, and the integration with the audit runner.

## Why this exists

The user's stated requirement: *"Define a clear solution and way of enforcing all we do here and my requests to be part of how what we build will work."*

Without a registry, decisions made in chat (or PRs, or ADRs) live as ungoverned prose. They're forgotten, contradicted, or quietly violated. The rule registry is the structural answer: every decision becomes a registry entry; every registry entry has at least one mechanical enforcer; the audit fails the build when the mapping has holes.

This is the **fitness-function pattern** from Neal Ford's *Building Evolutionary Architectures*, applied with a registry layer that maps ADRs to enforcers.

## Relationship to `principles.yaml` (the upstream source of truth)

`packages/principles/principles.yaml` is the **upstream source of truth** for principles (added in v1.5; see [mechanical-enforcement.md](./mechanical-enforcement.md)). The rule registry (`docs/rules/RULE-NNNN.yaml`) is the PR-trackable, finer-grained derivative used by the audit runner and admin RTM dashboard.

**The relationship:**

| `principles.yaml` (upstream) | `docs/rules/` (downstream) |
|---|---|
| Source of truth for principles | Derived rule entries, one per enforcer surface where useful |
| Categorized by meta / operating / architecture | Sequentially numbered (RULE-NNNN) |
| Edited directly by humans/AI | Generated by `pnpm principles:codegen` for principle-derived rules; can also be hand-authored for narrow rules that don't deserve a top-level principle |
| Carries severity + enforcer list | Carries the same enforcer schema |

**Workflow:**
1. Edit `packages/principles/principles.yaml` to add/modify a principle.
2. Run `pnpm principles:codegen` — this updates `docs/rules/RULE-*.yaml` for every enforcer surface where a derived rule is useful.
3. New narrow rules (e.g., "no `console.log` in production code") can be created independently in `docs/rules/` without a parent principle, but must include a self-justification in their `created-new-because:` field.
4. The audit-the-audits meta-check verifies: every principle in `principles.yaml` has ≥1 derived rule, every rule references either a principle ID or has its own justification, every enforcer location resolves.

**Both files use the same enforcer schema** so the audit runner processes them uniformly.

## Rule entry schema

`docs/rules/RULE-NNNN.yaml` — one file per rule, sequentially numbered.

```yaml
id: RULE-0042
statement: "All API routes must validate request body with Zod before handler logic."
adr: ADR-017                                       # the decision record
owner: group:finky
severity: blocking | error | warn | info
status: active | draft | deprecated
created_at: 2026-05-01
deprecated_by: null                                # RULE-NNNN if superseded
enhances: null                                     # OR a previous rule id this enhances
created_new_because: |
  No existing rule covered request-body validation; closest was RULE-0023
  (response-body validation). Different concern, different enforcer surface.
enforcers:
  - kind: eslint
    rule: csps/require-zod-body-validation
    file: tools/validators/eslint-rules/require-zod-body.ts
  - kind: runtime
    middleware: withZodValidation
    file: packages/db/src/middleware/with-zod.ts
  - kind: test
    suite: api-contract-tests
    file: tools/validators/api-contract.test.ts
```

## The chat → law workflow

When the user and an AI assistant agree on a decision in chat:

1. **AI generates the ADR** (per [adr-process.md](./adr-process.md) — uses MADR template).
2. **AI generates the rule entry** linked to the ADR.
3. **AI scaffolds the enforcer stub** with `// @enforces: RULE-NNNN` annotation.
4. **PR opens.** CI runs the registry audit + all enforcers + the new enforcer stub (which throws `NotImplementedError` — fails CI).
5. **AI (or user) implements the enforcer.** Stub becomes real check.
6. **Merge.** The rule is now law. Future violations fail the build.

A Mastra agent tool `proposeRule({ statement, enforcer_kind, severity })` automates steps 1–3.

## Bidirectional audit invariants

Two invariants the audit runner enforces every PR:

### Invariant 1: No orphan rules

For every rule in `docs/rules/`, at least one enforcer must exist:
```
for each rule R in registry:
  assert len(R.enforcers) >= 1, f"RULE-{R.id} has no enforcer"
  for each E in R.enforcers:
    assert exists(E.file), f"RULE-{R.id} enforcer {E.kind} references missing file {E.file}"
```

### Invariant 2: No orphan enforcers

For every enforcer in code (identified by `// @enforces: RULE-NNNN` annotation), the referenced rule must exist:
```
for each file F in source tree:
  for each // @enforces: RULE-NNNN annotation in F:
    assert exists(rule(NNNN)), f"{F} references missing RULE-{NNNN}"
    if rule(NNNN).status == 'deprecated':
      warn(f"{F} enforces deprecated RULE-{NNNN}")
```

These two invariants close the loop: rules without enforcers are noticed; enforcers without rules are noticed; deprecated rules still being enforced trigger warnings (signal to either reactivate or remove the enforcer).

## Enforcer kinds

The `enforcer.kind` field is a closed enum. Each kind has a known location pattern:

| Kind | Where it lives | When it runs |
|---|---|---|
| `eslint` | `tools/validators/eslint-rules/<name>.ts` | pre-commit + PR (changed files) |
| `runtime` | `packages/<pkg>/src/middleware/<name>.ts` OR `packages/<pkg>/src/<name>.ts` | every request |
| `zenstack` | `libs/policies/slices/**/*.zmodel` (`@@allow` rules) | every Prisma query |
| `nx-boundary` | `nx.json` `depConstraints` | PR |
| `test` | `tools/validators/<name>.test.ts` | CI (full suite) |
| `audit-check` | `libs/audits/checks/<name>.ts` (registered with audit runner) | per cadence (PR/nightly/weekly) |
| `pr-bot` | `tools/danger/<name>.ts` (Danger.js) | PR |
| `frontmatter` | implicit; checked by `validate-frontmatter.mjs` | PR + nightly |
| `generator-prompt` | `tools/generators/<gen>/index.ts` (catalog-first prompt) | every `nx g` invocation |
| `manual` | (escape hatch) | reviewer-asserted; audit warns if unchanged > 90 days |

## Initial seed rules (move existing principles into the registry)

The 27 architecture principles in [architecture-principles.md](./architecture-principles.md) become RULE-0001 through RULE-0027 (or grouped where multiple principles share an enforcer). The reuse-first principle becomes RULE-0024 with 7 enforcers (the 7 mechanical enforcers in [reuse-first-principle.md](./reuse-first-principle.md)).

Migration plan: as each pillar's content migrates from v1.3, principles become rules. Each ADR that locked a v1.3 decision becomes ADR-0001 through ADR-0030 (one per locked decision).

## Admin surface

`/admin/policies` — Payload-driven UI:

- Searchable, sortable table: `ID | Statement | ADR | Severity | Status | Enforcers | Last Result`
- Filter by status, severity, owner
- Click-through to: ADR markdown, enforcer source files, last 30 days of results
- Aggregate counts: active / deprecated / draft / orphan
- The "missing X has no enforcer" and "Y enforcer has no rule" alerts surfaced here

This is the platform's true requirements traceability matrix (RTM).

## Integration with the audit runner

The audit runner (per [audit-runner.md](./audit-runner.md)) gains four checks:

| Slug | Cadence | Severity | What it checks |
|---|---|---|---|
| `rule-registry-no-orphan-rules` | PR | error | Every rule has ≥1 enforcer |
| `rule-registry-no-orphan-enforcers` | PR | error | Every `@enforces:` annotation references a real rule |
| `rule-registry-deprecation-cleanup` | nightly | warn | Deprecated rules still enforced (cleanup signal) |
| `rule-registry-stale-manual-enforcers` | weekly | info | Manual enforcers unchanged > 90 days (re-verify signal) |

## Enforcement layers — the full stack

For any given concern, CSPS may have rules enforced at multiple layers. Example for "all entitlement checks must include excludedUserIds and includedUserIds":

- ESLint rule: identifiers `excludedUserIds`, `includedUserIds` must appear together
- Runtime middleware: `hasFeature()` always reads both
- ZenStack policy: `@@allow` reads both via `auth().entitlements`
- Audit check: surveys all `Entitlement` rows for inconsistent state

Each layer enforces a slice of the rule. Multiple enforcers per rule is normal and good.

## Reuse-first applied to rules themselves

Before proposing RULE-NNNN, search:
```bash
grep -ri "<your statement keywords>" docs/rules/
```

If a near-match exists, **enhance the ratified rule** by:
- Adding a new enforcer (most common)
- Refining the statement (requires ADR)
- Marking the old rule deprecated and creating a new one with `enhances: RULE-OLD` (rare, requires ADR)

The registry's own `enhances` field is what the catalog audits for the principle.

## Open questions

- **Granularity.** Does "use Zod for request bodies" become 1 rule or 1-per-route? Answer: **1 rule + N route-level enforcer instances**. The rule statement is the policy; per-route enforcement is just multiple ESLint rule applications.
- **Cross-stack rules.** A rule that spans both code (ESLint) and data (ZenStack `@@allow`) just declares multiple enforcers. The audit aggregates pass/fail across them — the rule fails if any enforcer fails.
- **AI-proposed vs human-written rules.** Add `proposed_by: ai | human` to frontmatter. AI-proposed rules require label `human-reviewed` on the PR before merge.
- **ZenStack vs Cerbos (long-term).** ZenStack handles all data-layer authz today. If/when an authz concern emerges that needs cross-cutting rules (e.g., "user X can edit doc Y because they're in team Z"), Cerbos joins the stack. Heuristic: if the policy needs `prisma`'s query context, it's ZenStack; if it's a stateless yes/no on principal+resource+action with no DB shape, it's Cerbos.
