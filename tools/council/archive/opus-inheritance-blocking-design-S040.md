# Inheritance Blocking Design — One Source, Protected Children

## The Problem (Governor directive)

"Make deep audit on having one source where each update updates other elements.
See what will make you and other AI use it always — not update one element separately.
Can you block the children? Allow specific modifications with special permission
without breaking the mini-tree?"

## Current State (audit finding)

**0 files** in apps/ or libs/ have inheritance declarations (`@csps-dna`, `inherits_from`, `template_version`).
The inheritance system is 100% paper-based. No blocking exists. Children can be freely edited.

The CSPS PACK (`profile-registry.yaml`) is the first canonical source. Its children
(to be built in S041) will be the first test of the blocking mechanism.

---

## WHY AI ALWAYS UPDATES CHILDREN SEPARATELY

The training default (DEFAULT-R3 from csps-development-reasoning.md):
- Trigger: Governor asks to fix/update a file
- Default: AI edits the specific file asked about
- Satisfaction point: "I've updated the file" — done
- CSPS Override needed: "Check if this file is a child. If yes: update parent first."

**What makes AI always use the one source:**
Three mechanisms must ALL be present:

1. **T1 hook** — fires BEFORE the edit, blocks if target is a registered child with stale template_version
2. **T2 validator** — fires at COMMIT, blocks commit if any child diverged from parent version
3. **T3 injection** — session-open.sh states: "CSPS PACK in profile-registry.yaml = canonical source. Never edit children directly."

Without T1 AND T2, AI will follow T3 for ~10 turns, then drift back to editing children directly.

## THE BLOCKING MECHANISM (Full Design)

### Layer 1: Child Registry (the inheritance-registry.yaml)

```yaml
# tools/config/inheritance-registry.yaml
# THE source that defines parent-child relationships.

trees:
  - id: csps-pack
    root: docs/plan/_handoff/VAULT/inner-ai-defaults/profile-registry.yaml
    root_version: "1.0"
    children:
      - path: tools/config/ai-profiling-triggers.yaml
        template_version: "1.0"  # must match root_version
        type: auto-generated     # regenerated by pnpm profiles:sync
        allow_direct_edit: false  # BLOCKED without special permission
      - path: .claude/hooks/user-prompt-submit-ai-profiler.sh
        template_version: "1.0"
        type: reads-from-child   # reads ai-profiling-triggers.yaml
        allow_direct_edit: false
      - path: docs/external/coworker-cooperation-plan.md
        template_version: "1.0"
        type: downstream-doc
        allow_direct_edit: false
    propagation_rules:
      auto_apply_risk: low   # low-risk changes auto-propagate
      requires_confirmation: [medium, high]
      block_without_ratification: [high]

  - id: apps-template
    root: apps/template/
    root_version: "1.0"
    children:
      - path: apps/habit-tracker/
        template_version: "1.0"
        type: forked-app
        allow_direct_edit: true   # apps CAN be edited directly (B_APPS_ARE_TRIALS)
        requires_component_b: true  # every app fix needs libs/ component
    propagation_rules:
      auto_apply_risk: none   # apps always need human review
```

### Layer 2: T1 Blocking Hook (pre-tool-use-inheritance-guard.sh)

```bash
# Fires on Write/Edit tool calls
# Reads inheritance-registry.yaml
# If target file is a registered child with allow_direct_edit: false:
#   → BLOCK with explanation + fix path

REGISTRY="tools/config/inheritance-registry.yaml"
TARGET_FILE="$1"  # the file being written/edited

# Check if file is a blocked child
IS_CHILD=$(node -e "
const yaml = require('js-yaml');
const reg = yaml.load(require('fs').readFileSync('$REGISTRY'));
for (const tree of reg.trees || []) {
  for (const child of tree.children || []) {
    if ('$TARGET_FILE'.endsWith(child.path) && !child.allow_direct_edit) {
      console.log(tree.id + '|' + tree.root);
      break;
    }
  }
}
")

if [ -n "$IS_CHILD" ]; then
  TREE_ID=$(echo $IS_CHILD | cut -d'|' -f1)
  ROOT=$(echo $IS_CHILD | cut -d'|' -f2)
  echo "[inheritance-guard] BLOCKED: $TARGET_FILE is a child in tree: $TREE_ID"
  echo "[inheritance-guard] Canonical source: $ROOT"
  echo "[inheritance-guard] To update this file:"
  echo "  1. Edit the parent: $ROOT"
  echo "  2. Run: pnpm inheritance:propagate --tree=$TREE_ID"
  echo "  3. Confirm propagation for affected children"
  echo "  4. Then commit ALL changes atomically"
  echo "[inheritance-guard] To override (emergency): add @csps-override-inheritance in commit message"
  exit 2  # BLOCKING
fi

exit 0
```

### Layer 3: T2 Validator (validate-inheritance-chain.mjs)

```javascript
// At commit time: scan all files with @csps-dna blocks
// For each file with inherits_from: field, check parent's current version
// If parent version > child's template_version: BLOCKING

// Output:
// BLOCKING: apps/habit-tracker/src/app/layout.tsx template_version=1.0 but parent=1.1
// Fix: run pnpm inheritance:propagate --tree=apps-template
```

### Layer 4: Special Permission (Override Mechanism)

**For emergency/justified direct edits:**

1. **Commit message override**: Include `[INHERITANCE-OVERRIDE: reason]` in commit message
   - The T2 validator reads commit message and skips blocking check if override present
   - Override is logged to `tools/council/inheritance-overrides.log`
   
2. **File-level override**: Add `# @csps-override-inheritance: reason` comment at top of file
   - The hook reads this comment and allows the edit (with warning)
   - The validator flags it for Governor review at next session

3. **Governor ratification**: A PROTO directive that explicitly authorizes a direct edit
   - `[PROTO: OVERRIDE-INHERITANCE | tree: csps-pack | file: ai-profiling-triggers.yaml | reason: emergency fix]`
   - Creates an exemption entry in the inheritance registry

## MAKING AI ALWAYS USE THE CANONICAL SOURCE

### Three-layer approach:

**T3 (session):** Session-open.sh injection:
```
INHERITANCE DISCIPLINE:
  The CSPS PACK (profile-registry.yaml) is the canonical source.
  NEVER edit children directly. ALWAYS update the parent first.
  Children: ai-profiling-triggers.yaml, ai-profiler hook, DNA bundle, Playground AI Personas.
  Violation: AI edits child → parent becomes stale → children drift apart → moat erodes.
```

**T1 (hook):** pre-tool-use-inheritance-guard.sh (described above)
- BLOCKING exit 2 for child edits without override

**T2 (validator):** validate-inheritance-chain.mjs
- BLOCKING at commit for any child with template_version < parent version

### What changes AI's behavior permanently:

The T1 hook is the key. AI cannot learn to "always update parent first" from T3 alone — context pressure erases it. When the T1 hook BLOCKS the edit and says "update parent first, then run pnpm inheritance:propagate", AI has no choice but to follow the process. The blocking itself teaches the correct sequence.

## THE MINI-TREE MODEL

```
profile-registry.yaml (CANONICAL ROOT)
├── ai-profiling-triggers.yaml (auto-generated, blocked)
│   └── user-prompt-submit-ai-profiler.sh (reads triggers, blocked)
├── DNA bundle output (pnpm dna:bundle, generated)
└── Playground AI Personas page (displays, blocked)

apps/template/ (CANONICAL ROOT)
├── apps/habit-tracker/ (forked, editable with component B requirement)
└── apps/future-app/ (forked, editable)

behavioral-contracts.md (CANONICAL ROOT)
├── behavioral-contracts/ B_*.md slices (auto-generated, blocked)
└── behavioral-contracts-index.yaml (auto-generated, blocked)
```

**What "blocked" means:**
- AI cannot directly edit without seeing BLOCKING message and fix path
- Commit fails if template_version doesn't match
- Override requires explicit `[INHERITANCE-OVERRIDE: reason]` or PROTO directive

**What "editable with component B" means (for app children):**
- Apps CAN be directly edited (B_APPS_ARE_TRIALS — apps are ephemeral)
- BUT every app fix must have a Component B (libs/ extraction)
- The validator checks component B exists before allowing commit
