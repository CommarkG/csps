# Combinatorial Engine — S1/S2/S3 Analysis

> Scope 1 = local content analysis
> Scope 2 = adjacent/connected implications
> Scope 3 = platform-wide/holistic implications

Not a plan. A quick deep dive. Saved before depth is lost.

---

## Scope 1 — Local (What is it?)

Six distinct parts in the raw concept:
- **P1:** Multi-dimensional context model — N dimensions, each with completeness score
- **P2:** Three collection modes — voluntary / organic-opportunity / humble-gap-fill
- **P3:** Response calibration — verbose → probe deeper; monosyllabic → back off
- **P4:** Forward reasoning — trajectory simulation from current vector state, not pattern matching
- **P5:** Trust architecture — declared-only, no surveillance, consent model essential
- **P6:** Polarity-as-complement — not "interrogate vs accept" but "actively, gradually complete"

Key novelty: it is an IMPLICATION engine, not a recommendation engine.
It reasons forward from current state to find collisions and opportunities the user cannot see.

---

## Scope 2 — Adjacent (What else does this touch?)

**Human Psychology Hub** — feeds directly into P3 (response calibration) and P2 (knowing WHEN and HOW to ask). Cannot be built without this foundation.

**AI Behavioral Profile** — mirror structure. Both profile their respective entity type with the same pattern: triggers, defaults, satisfaction points. The two profiles form a conversation model.

**Threshold (R1.4)** — the engine's input layer. Without Threshold classifying and routing inputs, the engine has no clean data to reason from.

**PE Engine / Queen timing** — the surfacing function IS a PE-with-timing decision: which insight to surface, when, at what confidence threshold.

**Session harvest / vault** — every past conversation is raw training material for the engine. The vault-as-neuronal-grid is the engine's memory.

**Playground profiling hub** — the UI layer. Developers and users need to see the dimensional model, know what's complete vs. missing, control what they've shared.

---

## Scope 3 — Platform-Holistic (What does this mean structurally?)

### Opportunity: Genuine differentiation
Most SaaS apps know what you do. This engine knows how you're doing. The moat is not technical — it's depth of understanding. Features are copied; this kind of cross-dimensional intelligence at this depth is not.

### Risk 1: Cold-start problem
Every new CSPS app starts at zero dimensional data. The engine needs to deliver value immediately or users disengage before it learns. Need: "minimum viable dimensional set" — the smallest set of declared information that enables meaningful forward reasoning. Must be designed before any implementation.

### Risk 2: Privacy architecture
If the personalization feels like surveillance, it destroys trust faster than anything. The declared-only model (P5) must be the non-negotiable foundation — not a later addition. Consent model must be airtight from the first interaction, not retrofitted.

### Structural implication: Extensible dimensional model
If the dimension list is hardcoded (a fixed schema), the engine can't evolve as user needs evolve. The dimensional model must itself be nodes in the vault graph — each dimension is a governance artifact, can be added/extended/deprecated through the same process as any platform element.

### BATCH-J amplification
Patterns learned in APP-001 about how cognitive-offload-professional users respond to certain dimensional questions → those patterns become available to APP-004. CAIE (Cross-App Intelligence Engine) is the Combinatorial Engine's compounding mechanism across apps. The engine improves with every new CSPS app.

### Prevention needed
Anti-pattern to watch: a simpler recommendation engine masquerading as a combinatorial one. The test: does it reason forward, or does it pattern-match? A Scope-3 check at ratification time.
